## 1. 产品概述

### 1.1 一句话定位

RPAS LMS 是一个面向**加拿大遥控驾驶航空器系统（RPAS / 无人机）驾驶员执照考试**的双语（英/中）在线学习与模拟考试平台，覆盖 Basic Operations 与 Advanced Operations 两个等级。

### 1.2 解决什么问题

加拿大交通部（Transport Canada）要求商用及特定场景下的无人机操作者持证飞行。考证者面临三个具体困难：

| 用户困难 | 产品对策 |
|---|---|
| 官方考试大纲分散在多份法规文件中，不成体系 | 按 8 个官方知识领域组织的结构化课程 |
| 缺乏贴近真实考试的练习环境（题量、时限、及格线、科目配比） | 严格对齐官方规格的模拟考试引擎 |
| 英语非母语者在法规术语上存在理解障碍 | 全站英/中双语，含题目、解析、课程正文 |
| Advanced 等级要求通过实操飞行审查（Flight Review），但找评审员困难 | 平台内的 Flight Review 时段预约 |

### 1.3 产品边界

本产品是**考试准备工具**，不是发证机构。平台的模拟考试成绩不具备任何官方效力，不能替代 Transport Canada 的正式考试。

### 1.4 知识域划分

全站内容按 8 个知识模块组织，该划分同时用于课程目录、题库归类与考试科目配比：

`air-law`（航空法规）、`airframes-systems`（机体与系统）、`human-factors`（人为因素）、`meteorology`（气象）、`navigation`（导航）、`flight-operations`（飞行操作）、`theory-of-flight`（飞行原理）、`radiotelephony`（无线电通话）

> 来源：`src/lib/content/types.ts` → `MODULE_IDS`

## 2. 目标与成功指标

> ⚠️ **本章的指标数值为建议基线，非实测数据。**产品目前尚未接入产品分析工具，以下指标**暂不可测量**。
> [U7](#u7--产品分析埋点-) 已决策接入 PostHog 并优先覆盖转化与学习两条漏斗——上线后本章指标即可测量。

### 2.1 北极星指标（North Star Metric）

**通过平台学习后成功取得执照的用户数。**

选择理由：它同时反映了内容质量、练习有效性和用户完成度，且与用户的真实目标完全对齐——用户不是来"用产品"的，是来"考过"的。

### 2.2 支撑指标

| 层级 | 指标 | 定义 | 建议目标 |
|---|---|---|---|
| 获客 | 游客体验转化率 | 完成 10 题免费体验 → 注册的比例 | ≥ 25% |
| 激活 | 注册转付费率 | 注册用户 → 购买 Advanced Bundle | ≥ 8% |
| 参与 | 课程完成率 | 完成全部课时的付费用户占比 | ≥ 40% |
| 参与 | 模考人均次数 | 付费用户平均完成的模拟考试场次 | ≥ 5 |
| 效果 | 模考及格率提升 | 用户第 1 次与第 5 次模考的分差 | ≥ +15 个百分点 |
| 商业 | Flight Review 附加率 | 付费用户中预约实操审查的比例 | ≥ 30% |
| 留存 | 7 日回访率 | 注册后 7 天内再次登录的比例 | ≥ 45% |

### 2.3 反指标（Guardrail Metrics）

需要监控、不得因追求上述指标而恶化的项：

- **题目质量投诉率** —— 不得为提高及格率而降低题目难度
- **AI 助手单用户成本** —— 见 [R-AIA-04](#r-aia-04-速率限制)
- **支付失败率** —— 任何超过 2% 的支付失败都应触发排查

### 实现记录（2026-08-25）· 与本章设计的三处偏离

实现过程中发现三处设计与代码现实冲突，均已按下述方式解决，**本章其余描述以代码为准**：

| # | 本章原设计 | 实际实现 | 原因 |
|---|---|---|---|
| 1 | `FlightReviewBooking.creditId String @unique`（§13.2） | **不加此列**，只保留 `FlightReviewCredit.bookingId` 单向链接 | §13.3 的四态判定全部只读券自己的列；而 §13.4 的「≥48h 退券」会把 `credit.bookingId` 置空。若预约侧还有一个**非空**的 `creditId`，退券后它就指向一张可能已被别人预约占用的券 —— 两个真相源，其中一个必然会漂移 |
| 2 | 一条部分唯一索引（`customerId WHERE status='BOOKED'`） | **两条**：另加 `slotId WHERE status='BOOKED'` | 取消从「删行」改成「置 `CANCELLED`」后，原有的 `slotId @unique` 会**永久锁死**被取消过的时段 —— 必须同样收窄到进行中的预约 |
| 3 | 手写 `prisma/migrations/` | `prisma/sql/*.sql` + `pnpm db:indexes` | 本项目实际用 `prisma db push`（`migrations/` 目录自 2026-06 起已停止维护）。索引改由独立脚本施加，测试建库与生产部署走同一条路径 |

### 5.1 账号与身份（R-ACC）

#### R-ACC-01 管理员与客户物理隔离

**需求**：管理员与普通客户存储于**两张物理独立的表**（`Admin` / `Customer`），不共享任何角色字段。

**业务规则**：
- 不存在"把客户提权为管理员"的数据路径——客户表根本没有角色列
- 两者的登录走不同的 NextAuth Provider（`credentials` vs `admin`）

**验收标准**：
- Given 一个 `Customer` 记录，When 尝试通过任何 API 修改其权限，Then 无任何字段可使其获得管理后台访问权
- Given 一个客户账号，When 用它登录 `/coriander`，Then 登录失败

> 来源：`prisma/schema.prisma`（`Admin` / `Customer`）、`auth.ts`

---

#### R-ACC-02 邮箱/手机验证码登录注册

**需求**：用户可通过邮箱或手机接收 6 位验证码完成注册或登录，无需预先设置密码。

**业务规则**：

| 规则项 | 值 |
|---|---|
| 验证码位数 | 6 位数字 |
| 有效期 | **10 分钟** |
| 最大尝试次数 | **5 次**，超出后该码作废 |
| 存储方式 | 哈希存储，不落明文 |
| 消费方式 | 一次性，验证成功即标记 `consumedAt` |
| 首次验证成功 | 自动创建 `FREE` 层级账号 |

**验收标准**：
- Given 已发送验证码，When 用户在 10 分钟内输入正确码，Then 登录成功；若账号不存在则创建 FREE 账号
- Given 已发送验证码，When 用户连续输入错误 5 次，Then 第 5 次返回 `too_many_attempts`，该码永久失效
- Given 验证码已过期，When 用户输入正确的码，Then 拒绝并提示重新获取

**发送频率限制**（[U8](#u8--验证码发送频率限制-) 决策，待实现）：

| 维度 | 限制 |
|---|---|
| 同一地址 | **60 秒内 1 次** |
| 同一地址 | **单日 10 次** |
| 同一 IP | 建议一并限制，防止遍历不同地址实施骚扰 |

达到限制时的响应**不得泄露该地址是否已注册** —— 统一返回相同提示。

**异常与边界**：
- 同一码被并发验证 → 数据库条件更新（`consumedAt: null` 作为条件）保证只有一次成功
- ⚠️ 发送频率限制**当前尚未实现**，可复用现有 `RateLimit` 表与 `hitRateLimit`

> 来源：`src/lib/auth/verificationCode.ts`

---

#### R-ACC-03 密码登录与登录锁定

**需求**：已设置密码的账号可用邮箱/手机/用户名 + 密码登录；连续失败触发锁定。

**业务规则**：

| 主体 | 失败阈值 | 计数窗口 | 锁定时长 | 锁定维度 |
|---|---|---|---|---|
| **客户** | 8 次 | 15 分钟 | 15 分钟 | 账号 + IP（IP 阈值为账号的 4 倍 = 32 次） |
| **管理员** | 5 次 | 15 分钟 | **30 分钟** | 账号 + IP（同阈值） |

- 锁定状态存储于**数据库**（`RateLimit` 表）而非内存，以便在无状态的 Serverless 实例间生效
- 登录成功后清除该账号与 IP 的失败计数
- **管理员开启 MFA 后，TOTP 码错误同样计入失败次数**

**验收标准**：
- Given 客户账号连续 8 次密码错误，When 第 9 次尝试（即使密码正确），Then 拒绝登录，持续 15 分钟
- Given 管理员已开启 MFA，When 密码正确但 TOTP 码错误，Then 登录失败**且失败计数 +1**
- Given 账号被锁定，When 从另一个 IP 用正确密码登录，Then 仍然被拒绝（账号维度锁定独立于 IP）

> 来源：`src/lib/auth/localAccount.ts`、`src/lib/auth/adminAccount.ts`、`src/lib/security/rateLimit.ts`

#### R-ACC-04 管理员双因素认证（MFA）

**需求**：管理员账号支持基于 TOTP 的双因素认证；开启后，密码单独不足以登录。

**业务规则**：
- 由管理员在 `/coriander/security` 自助开启
- 开启状态由 `Admin.totpEnabledAt` 标记
- 一旦开启，缺失或错误的 TOTP 码等同于密码错误

**验收标准**：
- Given 管理员已开启 MFA，When 仅提供正确密码而不提供 TOTP 码，Then 登录失败
- Given 管理员未开启 MFA，When 提供正确密码，Then 登录成功

**MFA 强制性**（[U9](#u9--管理员-mfa-不强制-) 决策）：**不强制。**管理员账号由 PO 手动指定，不对外开放注册。

> **残余风险**（已知悉并接受）：「账号不对外开放」消除的是未授权账号被创建的风险，而 MFA 防御的是**密码已泄露**的风险（钓鱼、密码复用、设备失陷）。两者针对不同威胁，后者仍然存在。现有补偿控制为登录锁定（5 次 / 15 分钟 → 锁 30 分钟，账号+IP 双维度），可抵御暴力破解，但无法抵御攻击者已持有正确密码的情形。
> 建议：即便不强制，也为实际在用的管理员账号开启 MFA —— 功能已实现，成本极低。

> 来源：`src/lib/auth/adminMfa.ts`、`SEC-16` 标记

---

#### R-ACC-05 第三方登录（OAuth）

**需求**：支持 Google 与 Apple 登录。

**业务规则**：
- 仅当对应的 `CLIENT_ID` / `CLIENT_SECRET` 环境变量存在时才注册该 Provider
- 未配置时，登录页**主动隐藏/禁用**对应按钮，避免用户跳转到第三方的 `invalid_request` 错误页

### 5.3 课时检查点（R-CKP）

#### R-CKP-01 检查点题库物理隔离

**需求**：课时检查点使用**与考试题库完全独立**的 `CheckpointQuestion` 表。

**业务规则**（安全关键 · `SEC-04`）：
- 检查点接口**只查询** `CheckpointQuestion` 表
- 考试题目的 ID 在此接口上**永远无法解析**，因此该公开接口在物理上不可能泄露考试答案
- 两个考试题库使用 `basic-` / `adv-` 前缀保证 ID 全局唯一

**验收标准**：
- Given 一个有效的考试题目 ID，When 提交到检查点校验接口，Then 返回 404（而非返回该题答案）

> 这是本产品最重要的安全设计之一：**用数据隔离代替权限判断**。权限判断可能写错，物理隔离不会。

#### R-EXM-02 按科目权重加权抽题

**需求**：试卷按知识模块的权重比例抽取题目，模拟真实考试的科目分布。

**业务规则**：

| 模块 | Basic 权重 | Advanced 权重 |
|---|---|---|
| air-law | 30% | 28% |
| flight-operations | 16% | 16% |
| human-factors | 12% | 12% |
| meteorology | 10% | 10% |
| navigation | 8% | 10% |
| airframes-systems | 10% | 8% |
| radiotelephony | 8% | 10% |
| theory-of-flight | 6% | 6% |

- 配额分配采用**最大余数法**（Largest Remainder），保证各科配额之和**精确等于**总题数
- 某科目题目不足时，缺口从剩余题池回填
- **同一份试卷内不重复出题**
- 抽题使用**带种子的随机数**，相同种子产生相同试卷（便于问题复现）

**验收标准**：
- Given Basic 考试 35 题，When 生成试卷，Then 各科目题数之和精确为 35
- Given 相同的种子与题库，When 两次生成试卷，Then 得到完全相同的题目序列

**异常与边界**：
- **题池充足性校验**（[U1](#u1--题池不足时拒绝创建考试-) 决策，待实现）：创建前校验 `可用题池 >= 所需题量`（**含等号**），不足则拒绝创建并返回明确错误
- ⚠️ **当前实现**：`generateExam` 在题池不足时返回 `min(总题量, 题池大小)`，静默生成题量不足的试卷；且 `scoreExam` 按**实际题量**计算及格线，会产生虚假的通过信号。对应 **DEF-003**

#### R-EXM-03 三层题池访问控制

**需求**：不同身份的用户从不同的题目子集中抽题。

**业务规则**（安全关键）：

| 身份 | Basic 题池 | Advanced 题池 |
|---|---|---|
| `PAID` | **全部难度** | **全部难度** |
| `FREE` | 仅 `difficulty === 1` | **空**（不可创建） |
| `GUEST` | 仅 `difficulty === 0` | **空**（不可创建） |

- 创建权限：`PAID` 可创建任意等级；`GUEST` / `FREE` 仅可创建 Basic
- Advanced 考试对非付费用户返回 403

**游客的题库规模要求**（[U4](#u4--考试次数策略-) 决策，待实现）：
游客题量为 **15 道**，从 `difficulty === 0` 池中**随机抽取**（抽取方式与其他档位一致）。该池应维护约 **20 道**以保留冗余——这使游客多次体验能看到不同题目，同时把可见题目总量控制在 20 道以内。

**题池充足性校验**（[U1](#u1--题池不足时拒绝创建考试-) 决策，待实现）：
创建考试前校验 `可用题池大小 >= 所需题量`，不足则**拒绝创建**并返回明确错误，不再静默降级生成题量不足的试卷。

**验收标准**：
- Given 未登录游客，When 创建 Basic 考试，Then 成功，返回 **15 题**，且全部为 difficulty 0
- Given difficulty 0 池维护为 20 道，When 游客多次创建考试，Then 所抽题目**全部落在这 20 道之内**（不溢出到其他难度）
- Given difficulty 0 池少于 15 道，When 游客创建考试，Then **拒绝创建**（题池校验对游客档同样适用）
- Given FREE 用户，When 创建 Basic 考试，Then 成功，返回 35 题，且全部为 difficulty 1
- Given FREE 用户，When 创建 Advanced 考试，Then 返回 403
- Given PAID 用户，When 创建 Advanced 考试，Then 成功，返回 50 题
- Given `difficulty === 1` 的题目少于 35 道，When FREE 用户创建 Basic 考试，Then **拒绝创建并返回明确错误**（不是返回一份不足 35 题的试卷）

**⚠️ 当前实现与本节的差异**：游客仍为随机抽 10 题；题池充足性校验尚未实现（对应 DEF-003）。

> 来源：`src/lib/domain/accessPolicy.ts` → `canCreateExam` / `questionsForAccess`

#### R-EXM-07 考试计时

**需求**：考试有时间限制，超时后不可继续作答。

**业务规则**（[U2](#u2--超时会话惰性结算-) 决策后的目标行为）：
- 会话创建时计算 `expiresAt = 开始时间 + 时限`
- **超时后 `answer` 接口拒绝写入**（返回 false）
- **超时后 `submit` 仍被允许**，按超时前已保存的答案判分
- 客户端计时器到点自动交卷 —— 提供即时体验
- **服务端惰性结算兜底**：读取会话时若发现 `已超时 && 未交卷`，**自动按已保存答案判分并落库**
- 用户重新进入已超时的会话时，直接展示结果页并标注「考试已超时，按超时前的作答判分」
- 结算结果带 `timedOut` 标记，供前端提示与后续统计区分

**为什么用惰性结算而非定时任务**：无需引入调度基础设施，结算发生在真正有人访问时；同时天然覆盖了「用户永远不再回来」的情况——那种会话本就无人关心，不结算也无影响。

**验收标准**：
- Given 考试已超时，When 调用作答接口，Then 返回失败，答案不被记录
- Given 考试已超时，When 调用交卷接口，Then 成功交卷，按超时前已保存的答案判分
- Given 用户在超时前关闭浏览器，When 之后查看考试历史，Then **该场考试已自动结算并出现在历史中**
- Given 用户重新进入已超时的会话，When 页面加载，Then 展示结果页并显示超时说明
- Given 两个请求并发读取同一个已超时会话，When 触发惰性结算，Then **只结算一次**，两者得到相同成绩

**⚠️ 当前实现与本节的差异**：惰性结算**尚未实现**。当前用户关闭浏览器后，会话永久停留在未交卷状态，作答事实上丢失。对应 **DEF-002**。

> 来源：`src/lib/exam/service.ts` L80-104（现状）；目标行为见 [U2 决策](#u2--超时会话惰性结算-)

- 注册或首次登录成功时，将该 `sessionId` 一并提交后端
- 后端**严格校验**后写入新用户的 `userId`
- 认领后该会话进入正常的所有权体系

**认领的校验条件**（全部满足才允许）：
1. 会话存在
2. `userId === null`（**确实是无主会话**）
3. 未超过 24 小时有效期

**验收标准**：
- Given 游客完成体验后注册，When 提交其会话 ID，Then 该考试出现在新账号的考试历史中
- Given 一个**已有所有者**的会话 ID，When 任意用户尝试认领，Then **拒绝**
- Given 一个已过期的无主会话，When 尝试认领，Then 拒绝

> ⚠️ **第 2 条校验是安全关键**。若允许认领已有所有者的会话，等同于「任何人都能把他人的考试记录据为己有」——这是一个越权漏洞，而非功能缺陷。

### 5.5 支付与权益（R-PAY）

#### R-PAY-01 两个可售商品

**需求**：平台销售两个独立商品。

| 商品代码 | 名称 | 作用 |
|---|---|---|
| `paid_access` | Advanced Bundle | 解锁全部课程、全部题库、Advanced 考试 |
| `flight_review` | Flight Review | 单独购买实操审查资格 |

**业务规则**：
- `flight_review` 为**独立附加品**，购买后**不改变** `accessTier`
- 购买 `paid_access` 的用户**自动获得**预约 Flight Review 的资格（无需另行购买）

**重复购买规则**（[U13](#u13--重复购买与-flight-review-消耗品模型-) 决策，待实现）：

| 场景 | 处理 |
|---|---|
| 已持有 `paid_access` 的用户再次购买**课程** | **拦截** —— 课程是永久权限，重复购买无意义 |
| 购买 Flight Review 且**当前有可用券** | 提示「你当前有 N 张可用审查券」并**引导至预约页**，但**保留继续购买的出口** |
| 购买 Flight Review 且**无可用券** | **正常购买**，不拦截 |

> **两类商品的重复购买规则不同，因为它们的性质不同**：
> `paid_access` 是**永久权限**，买第二次得不到任何东西 → 拦截。
> `flight_review` 是**一次性消耗品**（U13 决策），买第二次得到第二次机会 → 允许。第二行的提示只为**防止误购**（用户可能忘了自己还有券），不是禁止。

**验收标准**：
- Given 已持有 paid_access 的用户，When 再次发起课程购买，Then **不创建 Stripe 结账会话**，返回明确提示
- Given 用户有 1 张可用券，When 发起 Flight Review 购买，Then 提示可用券数并引导至预约页，**且仍可选择继续购买**
- Given 用户可用券为 0，When 发起 Flight Review 购买，Then 正常创建结账会话，无任何拦截

> 来源：`src/lib/payments/config.ts`、`src/lib/payments/entitlements.ts`

#### R-PAY-02 权益是唯一真相源

**需求**：`Entitlement` 表是权益的唯一真相源；`Customer.accessTier` 仅为反规范化缓存。

**业务规则**：
- `hasPaidAccess(userId)` 判定逻辑：**存在未撤销的 `paid_access` 权益** `OR` **`accessTier === "PAID"`**
- 该 OR 逻辑是容错设计：即使缓存未同步，权益记录仍能保证用户可用
- 会话中的 `accessTier` 在显式 `session.update()` 时从权益表重新推导，**使购买后无需重新登录即可生效**

**验收标准**：
- Given 用户持有未撤销的 paid_access 权益但 accessTier 为 FREE，When 判定付费权限，Then 返回 true
- Given 用户完成购买，When 触发会话更新，Then 无需重新登录即可访问付费内容

**一致性保障**（[U5](#u5--补齐权益撤销与退款流程-) 决策，待实现）：
- 撤销权益时**必须在同一事务内**同步重置 `accessTier`，否则 OR 逻辑会让撤销静默失效
- 增加**权益与缓存的一致性巡检**，发现不一致时告警

> 来源：`src/lib/payments/entitlements.ts`、`auth.ts`

#### R-PAY-03 Webhook 幂等

**需求**：Stripe Webhook 事件的处理必须幂等，重复投递不重复发放权益。

**业务规则**：
- 已处理的事件 ID 记录于 `WebhookEvent` 表
- 重复事件直接跳过
- 支付记录以 `stripeCheckoutSessionId` 为唯一键 upsert

**验收标准**：
- Given 同一 Stripe 事件被投递两次，When 处理，Then 权益只发放一次，支付记录只有一条

> 来源：`app/api/payments/webhook/route.ts`

---

#### R-PAY-04 管理员权益授予与撤销

**需求**：管理员可手动授予或撤销 `flight_review` 权益。

**业务规则**：
- 授予操作幂等；对已撤销的权益执行授予会**取消撤销标记**
- 撤销为软删除（标记 `revokedAt`），不删除记录

**`paid_access` 的撤销**（[U5](#u5--补齐权益撤销与退款流程-) 决策，待实现）：
- 补齐 `revokePaidAccessEntitlement`
- **必须在同一个事务内同时重置 `accessTier` 为 `FREE`** —— 否则因 `hasPaidAccess` 的 OR 判定逻辑，仅撤销权益记录会导致撤销**静默失效**

**验收标准**：
- Given 用户持有 flight_review 权益，When 管理员撤销，Then 该用户失去预约资格
- Given 用户持有 paid_access 权益，When 管理员撤销，Then 权益与 `accessTier` **在同一事务内一并更新**，用户立即失去付费权限
- Given 撤销操作中途失败，When 事务回滚，Then 权益与 `accessTier` **保持一致**（不出现半撤销状态）

**⚠️ 当前实现与本节的差异**：`paid_access` 的撤销**完全没有实现**，对应 **DEF-001**。

> 来源：`src/lib/payments/entitlements.ts`

#### R-PAY-05 退款申请与审核 ⬜ 未实现

**需求**：用户可申请退款，由管理员审核后人工确认执行。

**业务规则**（[U5](#u5--补齐权益撤销与退款流程-) 决策）：

| 角色 | 能力 | 位置 |
|---|---|---|
| 用户 | 提交退款申请 | Dashboard → Account Security |
| 管理员 | 审核资格、批准或拒绝、**人工确认执行退款** | `/coriander` 退款处理 section |

- 退款**不自动执行** —— 必须经管理员人工确认
- 申请状态：申请中 → 已批准 / 已拒绝 → 已退款
- 实际资金退款通过 **Stripe API** 发起，而非仅在本地标记状态
- Stripe 退款成功的回调应**触发权益撤销**（调用 R-PAY-04 的撤销能力），形成闭环

**验收标准**：
- Given 已付费用户，When 提交退款申请，Then 生成一条申请记录，状态为「申请中」
- Given 待审核的申请，When 管理员批准并确认执行，Then 通过 Stripe 发起退款
- Given Stripe 退款成功回调到达，When 处理该事件，Then **权益被撤销且 `accessTier` 重置为 FREE**
- Given 管理员拒绝申请，When 用户查看，Then 看到拒绝状态，**权益保持不变**

**实现要点**：
- 建议新增 `RefundRequest` 表记录申请与审核轨迹
- 建议同时接入 `charge.dispute.created`（支付争议）—— 争议场景下用户不会走申请流程，需要单独的处理路径
- 一致性巡检：定期比对 `Entitlement` 与 `accessTier`，发现不一致时告警

**Flight Review 退款的特殊处理**（[U13](#u13--重复购买与-flight-review-消耗品模型-) 决策后）：

| 券状态 | 退款处理 |
|---|---|
| 可用 | 撤销该券（写入 `revokedAt`），正常退款 |
| 占用中 | **先取消关联预约释放时段**，再撤销券 |
| **已消耗** | 审查已完成，**原则上不予退款** —— 由管理员人工判断 |

> 这正是 U5 决定「退款须经管理员审核」的价值所在：**券是否已消耗，直接决定该笔退款是否合理**。自动退款无法做这个判断。

#### R-FRV-02 预约资格

**需求**：仅具备资格的用户可预约。

**业务规则**（[U13](#u13--重复购买与-flight-review-消耗品模型-) 决策后的目标模型）：

```
canBookFlightReview = 存在可用券  AND  当前无未完成（BOOKED）的预约
```

- 该判定是仪表盘、预约页、所有预约接口的**唯一资格来源**
- 购买课程（Advanced Bundle）时**自动发放 1 张券**，因此 PAID 用户仍能预约——但**通过持券而非通过课程权限**

**验收标准**：
- Given 购买了 Advanced Bundle 的用户，When 访问预约页，Then 可以预约（课程已赠 1 张券）
- Given 用户的赠券已消耗且未再购买，When 尝试预约，Then **拒绝**，引导至购买页
- Given 用户持有可用券但已有一个 BOOKED 预约，When 尝试预约新时段，Then 拒绝（同时只能一个）

**⚠️ 当前实现与本节的差异**：现为 `持 flight_review 权益 OR 有课程权限`，**不存在券的概念**。改造涉及 `hasPaidAccess` 的 OR 分支拆除。

> 来源：`src/lib/payments/entitlements.ts` → `canBookFlightReview`（现状）

---

#### R-FRV-03 一人一约与时段独占

**需求**：一个用户同时只能有一个有效预约；一个时段只能被一人预约。

**业务规则**（[U13](#u13--重复购买与-flight-review-消耗品模型-) 决策后）：

| 规则 | 保证方式 | 变化 |
|---|---|---|
| 一个时段只能被一人预约 | `slotId @unique`（**数据库层**） | 不变 |
| 一个学员同时只能有一个未完成预约 | **应用层判断**（`status = BOOKED` 的记录数 ≤ 1） | ⚠️ **由数据库层降级为应用层** |
| 预约需持券 | 应用层 + `creditId @unique` | 新增 |

- 预约不再等同于「记录存在」：记录带 `status`，取消 = 状态置 `CANCELLED`（**保留记录**），改期 = 修改 `slotId`
- 保留历史记录是消耗品模型的必需——用户会有多次预约

**验收标准**：
- Given 两个用户并发预约同一时段，When 同时提交，Then 只有一个成功（`slotId @unique` 保证）
- Given 用户已有 BOOKED 预约，When 预约另一时段，Then **拒绝**（不再是"视为改期"；改期需显式操作）
- Given **同一用户并发发起两个预约请求**，When 同时提交，Then **只有一个成功**

> ⚠️ **最后一条是本次改动引入的新风险。**
> 移除 `customerId @unique` 后，「一人一约」从数据库约束降级为应用层判断，而应用层的「检查 → 写入」之间存在**竞态窗口**。必须用事务 + 适当的隔离级别（或对 customerId 加锁）来关闭这个窗口，并且**必须有并发用例验证**。
> 这是一个典型的教训：把数据库约束换成应用层判断，等于把「不可能发生」变成了「大概率不发生」。

**⚠️ 当前实现与本节的差异**：现为 `customerId @unique` + `upsert`（再次预约即改期），无 status 字段、无历史记录。

> 来源：`prisma/schema.prisma`、`src/lib/flightReview/booking.ts`（现状）

---

#### R-FRV-04 预约通知邮件

**需求**：预约、改期、取消时向用户发送邮件通知。

**业务规则**：
- 通过 Resend 发送
- 邮件内容按用户语言本地化
- 用户输入内容需 HTML 转义后嵌入邮件

**通知失败的处理**（[U12](#u12--通知失败时的处理-) 决策，待实现）：
- 邮件发送失败**不回滚预约** —— 预约是核心，通知是辅助
- **记录发送失败**并提供**重发入口**（用户端与管理端各一）
- **预约详情页必须成为唯一可信来源**：用户不打开邮箱也能看到完整的时间、地点、评审员信息
- 邮件发送须在预约事务**之外**执行，避免邮件服务超时拖长事务

#### R-FRV-06 审查券（Flight Review Credit） ⬜ 未实现

**需求**：Flight Review 资格以**可消耗的券**形式存在，一次购买对应一次审查机会。

**业务规则**（[U13](#u13--重复购买与-flight-review-消耗品模型-) 决策）：

*发放*

| 触发 | 发放 | source |
|---|---|---|
| 购买 `flight_review` | 1 张 | `stripe_checkout` |
| 购买 `paid_access`（课程） | **1 张** | `course_bundle` |
| 管理员授予 | 1 张 | `admin_grant` |

*券的四种状态*

| 状态 | 判定 |
|---|---|
| 可用 | `bookingId = null` 且 `consumedAt = null` 且 `revokedAt = null` |
| 占用中 | `bookingId` 指向一个 `BOOKED` 预约 |
| 已消耗 | `consumedAt` 已写入 |
| 已撤销 | `revokedAt` 已写入（退款收回） |

*消耗与退回*

- 预约时**绑定**一张可用券（占用中），**不立即消耗**
- 改期**不消耗新券**，原券继续占用
- 取消：距 `slot.startsAt` **>= 48 小时退回**，**< 48 小时消耗**
- 审查完成（或 `NO_SHOW`）→ 券**永久消耗**

**验收标准**：
- Given 用户购买课程，When 支付完成，Then **自动获得 1 张可用券**
- Given 用户有 1 张可用券，When 预约成功，Then 该券转为「占用中」，可用券数变为 0
- Given 预约在开始前 **49 小时**取消，Then 券**退回**为可用
- Given 预约在开始前 **47 小时**取消，Then 券**被消耗**，不退回
- Given 管理员标记审查完成，Then 券写入 `consumedAt`，预约状态转 `COMPLETED`

**⚠️ 48 小时是一条硬边界，判定为 `>=`**（PO 确认：48 小时及以上都退）。必须有对应的边界用例（47h59m / 48h 整 / 48h01m）。

---

#### R-FRV-07 预约完成标记 ⬜ 未实现

**需求**：管理员 / 评审员手动标记审查是否完成。

**业务规则**：
- 状态取值：`BOOKED` → `COMPLETED` / `CANCELLED` / `NO_SHOW`
- `COMPLETED` 与 `NO_SHOW` 均**消耗券**
- **不按时间自动完成** —— 需人工确认学员实际到场

**为什么不自动完成**：时段过去不代表审查发生。自动完成会把爽约也算作已完成，学员因此损失一次机会却无从申诉；反过来若一律不消耗，则爽约无成本，评审员时间会被反复浪费。`NO_SHOW` 状态正是为区分这两种情况而设。

**验收标准**：
- Given 一个已过期但未标记的 `BOOKED` 预约，When 查询，Then 状态**仍为 BOOKED**（不自动流转）
- Given 管理员标记 `NO_SHOW`，Then 券被消耗，学员需重新购买才能再约

### 5.9 原生移动端 API（R-MOB）

#### R-MOB-01 独立的 Bearer Token 鉴权

**需求**：原生移动端使用独立于 Web Cookie 会话的鉴权体系。

**业务规则**：

| 规则项 | 值 |
|---|---|
| 令牌形式 | 登录时返回的不透明字符串 |
| 存储方式 | **SHA-256 哈希后存储**，服务端不保留明文 |
| 有效期 | **30 天** |
| 撤销 | 支持（`revokedAt`） |
| 传递方式 | `Authorization: Bearer <token>` |

**验收标准**：
- Given 有效令牌，When 请求移动端接口，Then 正常返回
- Given 已撤销或已过期的令牌，When 请求，Then 拒绝

> 来源：`src/lib/mobile/session.ts`

---

#### R-MOB-02 功能对等

**需求**：移动端 API 覆盖 Web 端的核心学习与考试能力（账号、仪表盘、课程、课时、考试、检查点、进度、Flight Review）。

**⚠️ 关键风险**：移动端是一套**与 Web 并行的独立实现**。两套实现存在**行为漂移**风险——同一业务规则可能在一侧被修改而另一侧遗漏。

**业务规则**：所有在 Web 端生效的权限与安全规则（R-EXM-03、R-EXM-05、R-LRN-03），在移动端必须**完全等效**。

> 来源：`app/api/mobile/*`

### U1 · 题池不足时拒绝创建考试 ✅

**决策**：
1. 题池不足以生成完整试卷时，**拒绝创建考试**并返回明确错误，不再静默降级
2. CMS 增加**题库健康度检查**，各难度题量低于阈值时向管理员告警

**影响的需求**：R-EXM-02、R-EXM-03 需补充「题池校验」规则；新增 R-CMS-03（题库健康度检查）

**实现要点**：
- 校验位置应在 `service.ts` 的 `createMock` 内、`generateExam` 调用**之前** —— 先判断 `scopedBank.questions.length >= total`，不足则抛出可识别的错误
- 路由层将该错误转为 **409**（资源状态不满足）或 **503**（服务暂时不可用），**不要用 500**
- 错误文案面向用户，不暴露题库内部结构（如「当前题库不足以生成完整试卷，请稍后再试」）
- 需为三档分别设阈值：GUEST 因 U4 改为固定题库，此风险自动消除；**FREE 档（difficulty 1 需 ≥ 35 道）是当前真正的风险点**

**用例影响**：TC-EXM-51/52 的预期从「⚠️ 静默降级」改为「拒绝创建并返回明确错误」；TC-EXM-53 同理

### U2 · 超时会话惰性结算 ✅

**决策**：
1. 服务端在**读取会话时校验超时状态**，超时且未交卷则**自动按已保存答案判分并落库**（惰性结算，无需定时任务）
2. 用户重新进入超时会话时，**直接展示结果页**并标注「考试已超时，按超时前的作答判分」
3. **保留**当前的客户端自动交卷作为即时体验，服务端结算作为兜底
4. 沿用现有 `ExamSession`，**不引入新的会话概念**

**关于第 4 点**：`ExamSession.id` 即会话标识，`createMock()` 返回的 `sessionId` 就是它。惰性结算在现有结构上即可完成 —— 判断 `expiresAt <= now && !submitted` 后直接结算，无需新表、无需定时任务。

**影响的需求**：R-EXM-07 需重写；R-EXM-08（交卷幂等）保持不变

**实现要点**：
- 结算入口应覆盖**所有**读取会话的路径（`getSessionMeta` / `getReview` / 结果查询 / 考试历史），否则会出现「从 A 入口进已结算、从 B 入口进仍悬挂」的不一致
- 结算逻辑复用现有 `submit()`，避免出现第二套判分路径
- 结算需**幂等**：并发读取同一超时会话不得产生两次结算
- 结果需带标记（如 `timedOut: true`），供前端显示超时提示，并可用于后续统计区分

**用例影响**：TC-EXM-45/46 的预期从「⚠️ 永久悬挂」改为「自动结算并出现在考试历史中」；需新增「并发读取超时会话只结算一次」的用例

### U4 · 考试次数策略 ✅

**决策**（2026-08-24 初次决策，同日修订）：
1. **付费用户不设次数限制** —— 多练是产品价值所在
2. **游客题量由 10 提升至 15 题**
3. **题库保留冗余**：`difficulty === 0` 维护约 **20 道**，每次从中**随机抽取 15 道**

**这是一处行为变更**，与当前实现的差异只在题量：

| | 当前实现 | 决策后 |
|---|---|---|
| 游客题量 | 10 题 | **15 题** |
| 抽题方式 | 从 difficulty 0 池随机抽取 | **不变**（仍为随机抽取） |
| 题库规模要求 | 无明确要求 | **建议维护 20 道**（硬性下限 15） |
| 重复体验 | 每次题目可能不同 | **每次题目可能不同**（保持） |

> **修订说明**：初次决策为「固定 15 道，每次相同、仅打乱顺序」。修订后改为「20 道池中随机抽 15」，因此**「每次题目相同」不再成立**。
> 曝光控制仍然有效：游客无论刷多少次，可见题目上限为该 20 道，不会溢出到整个题库。

**影响的需求**：R-EXM-01（游客题量 10 → 15）、R-EXM-03（题库规模要求）

**实现要点**：
- **代码改动极小**：`GUEST_BASIC_QUESTION_COUNT` 由 `10` 改为 `15`，**抽题逻辑无需改动** —— 当前 GUEST 走的就是「从 difficulty 0 池随机抽 N 道」

- **游客侧的 U1 风险依然存在**：若 difficulty 0 的题目少于 15 道，仍会触发题池不足。健康度告警需覆盖此档

### U13 · 重复购买与 Flight Review 消耗品模型 ✅

**决策**（2026-08-24）：

| 场景 | 处理 |
|---|---|

| 取消预约 | **距开始 >= 48 小时退券**，< 48 小时不退 |
| 同时未完成的预约 | **最多 1 个** |

这是本文档中**改动面最大的一项决策**——它把 Flight Review 的资格模型从「持有权益」整体换成「持有可消耗的券」。

#### 13.1 资格模型的变化

```
旧模型   canBookFlightReview = 持 flight_review 权益  OR  有课程权限
新模型   canBookFlightReview = 存在可用券  AND  当前无未完成预约
```

> ⚠️ **`hasPaidAccess` 的 OR 分支必须从预约资格中拆掉。**
> 旧模型下 PAID 用户靠「有课程权限」直接获得预约资格；新模型下 PAID 用户**也必须持券**，因此购买课程时需自动发放 1 张券。
> `hasPaidAccess` 本身（用于课程、考试、AI 助手的判定）**保持不变**。

#### 13.2 数据模型

**新增 `FlightReviewCredit`（审查券）**：

```prisma
model FlightReviewCredit {
  id         String    @id @default(cuid())
  customerId String
  customer   Customer  @relation(fields: [customerId], references: [id], onDelete: Cascade)
  source     String    // "stripe_checkout" | "course_bundle" | "admin_grant" | "migration"
  paymentId  String?   // 来源支付；admin_grant / migration 时为空
  bookingId  String?   @unique  // 当前占用它的预约
  consumedAt DateTime? // 永久消耗时间
  revokedAt  DateTime? // 退款撤销
  createdAt  DateTime  @default(now())

  @@index([customerId])
}
```

**改造 `FlightReviewBooking`**：

```prisma
model FlightReviewBooking {
  id          String    @id @default(cuid())
  slotId      String    @unique   // 保留：一个时段仍只能一个预约
  customerId  String              // ← 去掉 @unique（需支持历史预约）
  creditId    String    @unique   // 占用的券
  status      String    @default("BOOKED")  // BOOKED | COMPLETED | CANCELLED | NO_SHOW
  completedAt DateTime?
  cancelledAt DateTime?
  createdAt   DateTime  @default(now())
  updatedAt   DateTime  @updatedAt

  @@index([customerId])
  @@index([customerId, status])
}
```

> ⚠️ **去掉 `customerId @unique` 是本次改动中风险最高的一步。**
> 该唯一约束此前在**数据库层**保证了「一人一约」。直接移除会把这条规则降级为**应用层判断**，而应用层的「检查 → 写入」之间存在竞态窗口。
>
> **✅ 决策（PO 2026-08-25）：用部分唯一索引把约束拉回数据库层。**
>
> ```sql
> CREATE UNIQUE INDEX "FlightReviewBooking_active_customer_key"
>   ON "FlightReviewBooking"("customerId")
>   WHERE status = 'BOOKED';
> ```
>
> 这样既支持历史记录（同一用户可有多条 `CANCELLED` / `COMPLETED`），又保留数据库级的「同时只能一个进行中预约」保证，应用层无需加锁。
> Prisma schema 目前不支持声明带 `WHERE` 的部分索引，需通过**手写 migration**添加；`prisma db push` 不会创建它，因此**测试环境的建库流程也必须包含这条索引**，否则并发用例在本地会假通过。

#### 13.3 券的状态机

一张券在任一时刻处于四种状态之一：

| 状态 | 判定条件 | 含义 |
|---|---|---|
| **可用** | `bookingId = null` 且 `consumedAt = null` 且 `revokedAt = null` | 可用于预约 |
| **占用中** | `bookingId` 指向一个 `BOOKED` 预约 | 已绑定预约，尚未完成 |
| **已消耗** | `consumedAt` 已写入 | 审查完成，或超期取消 |
| **已撤销** | `revokedAt` 已写入 | 退款收回 |

**状态迁移**：

```
可用 ──[预约]──► 占用中 ──[审查完成]────────► 已消耗
                    │
                    ├─[取消 · 距开始 >= 48h]─► 可用      （退券）
                    └─[取消 · 距开始 < 48h]──► 已消耗    （不退）

可用 ──[退款]──► 已撤销
```

---

#### 13.4 业务规则

**发券**：

| 触发 | 发放 | source |
|---|---|---|
| 购买 `flight_review` | 1 张 | `stripe_checkout` |
| 购买 `paid_access`（课程） | **1 张** | `course_bundle` |
| 管理员授予 | 1 张 | `admin_grant` |

**预约**（须同时满足）：
1. 存在**可用券**
2. **当前无 `BOOKED` 状态的预约**
3. 时段有效（`ACTIVE` 且未过期）且未被他人占用

预约成功时，将一张可用券绑定到该预约（`credit.bookingId = booking.id`）。

**改期**：只修改 `slotId`，**不消耗新券**，原券继续占用。

**取消**：以 `slot.startsAt` 与取消时刻的间隔判定——

| 间隔 | 券 | 预约状态 |
|---|---|---|
| **>= 48 小时** | **退回**（`bookingId` 置空） | `CANCELLED` |
| **< 48 小时** | **消耗**（写入 `consumedAt`） | `CANCELLED` |

**完成**：由管理员 / 评审员手动标记 → 预约状态 `COMPLETED`，券写入 `consumedAt`。

> 为什么由人工标记而非按时间自动完成：需要确认学员**确实到场**。自动完成会把爽约（no-show）也算作已完成。`NO_SHOW` 状态预留给这种情况，其券按「已消耗」处理。

#### 13.5 重复购买规则（修正）

> ⚠️ **本节修正了初次决策。**「PAID 用户购买 Flight Review → 提示已拥有并跳转」是在**方案 A（永久资格）**语境下做出的。
> 在消耗品模型下，PAID 用户用完赠券后**再次购买是合理需求**，不应拦截。

| 场景 | 处理 |
|---|---|
| 已持 `paid_access` 的用户再次购买**课程** | **拦截**（课程是永久权限，重复购买无意义） |
| 用户购买 Flight Review 且**当前有可用券** | 提示「你当前有 N 张可用审查券」并**跳转预约页**，同时**允许继续购买** |
| 用户购买 Flight Review 且**无可用券** | **正常购买**，不拦截 |

> 第二行的设计意图是**防止误购**而非禁止购买：用户可能忘了自己还有券。提示后仍应保留「仍要购买」的出口。

#### 13.6 数据迁移

上线时需要一次性迁移，否则现有用户会**失去已付费获得的资格**：

| 现有数据 | 迁移动作 |
|---|---|
| 持未撤销 `flight_review` 权益的用户 | 发 1 张券（`source: migration`） |
| `accessTier = PAID` 或持 `paid_access` 权益的用户 | 发 1 张券（`source: course_bundle`） |
| 现有的 `FlightReviewBooking` | 绑定到该用户的一张券；按 `slot.startsAt` 是否已过判定初始状态为 `COMPLETED` 或 `BOOKED` |

> **同时满足前两条的用户会获得 2 张券**——这是正确的，他确实付了两笔钱。

**`flight_review` 类型的 `Entitlement` 在迁移后废弃**：资格判定改看券，不再看权益。`hasFlightReviewEntitlement` / `grantFlightReviewEntitlement` / `revokeFlightReviewEntitlement` 相应替换为券的操作。`paid_access` 的 Entitlement **保持不变**。

#### 13.7 与退款流程（U5）的衔接

退款 Flight Review 时，需按券的状态分别处理：

| 券状态 | 退款处理 |
|---|---|
| 可用 | 撤销该券（写入 `revokedAt`），正常退款 |
| 占用中 | 先取消关联预约释放时段，再撤销券 |
| **已消耗** | **审查已完成，原则上不予退款** —— 由管理员人工判断 |

> 这正是 U5 决定「退款须经管理员审核」的价值所在：券是否已消耗，直接决定该笔退款是否合理。

## 12. 不做什么（Out of Scope）

明确划出边界，避免需求蔓延：

| 不做 | 理由 |
|---|---|
| 官方执照签发 | 平台无发证资质；仅做备考工具 |
| 直播 / 真人授课 | 与当前自学定位不符，运营成本模型完全不同 |
| 社区 / 论坛 / 用户互动 | 需要内容审核投入，且与备考核心价值弱相关 |
| 其他国家的无人机执照 | 法规体系完全不同，等同于新产品 |
| 无人机飞行模拟器 | 技术栈与产品定位差异过大 |
| 企业批量采购 / 团队管理 | 有价值但需独立的组织账号体系，列入后续评估 |
| 题目众包 / 用户贡献题目 | 题目准确性直接关系用户考试结果，须由专业人员把关 |
