## 发布流程

```
代码冻结 → 全量回归 → 缺陷收敛 → 准入检查表 → Go/No-Go → 发布 → 生产冒烟 → 观察期
                ↑                                    │
                └──────── No-Go：修复后重新回归 ◄─────┘
```

**"缺陷收敛"不等于零缺陷**，而是：**没有未决的 P0/P1，且全部剩余缺陷已被明确接受并记录在案。**

## 2. Go/No-Go 会议

### 2.1 QA 该说什么

**不是"测完了，可以发"。**那五个字是新手 QA 与资深 QA 最明显的分水岭。

正确的陈述结构是：**做了什么 → 没做什么 → 风险是什么 → 我的建议 → 需要谁拍板**

#### 陈述模板

```
本轮共执行 __ 条用例，通过 __ 条，通过率 __%。

【已测范围】
- A、B、C

【未测范围及原因】
- D（时间不足）
- E（环境不具备）

【已知遗留缺陷】
- 共 __ 个，其中 P2 __ 个、P3 __ 个
- 最坏情况下的影响是：______

【我的建议】
建议发布 / 建议延期 / 建议关闭 X 功能后发布

【需要确认】
请 @PO 确认是否接受上述 __ 个 P2 缺陷的风险。
若决定发布，建议同时准备好 ______ 的回滚方案。
```

### 2.2 QA 有没有否决权？

**大多数情况下没有绝对否决权，但有"记录在案的反对"。**

这不是弱势，而是正确的责任划分——发布是商业决策，需要权衡收入、竞品、对客户的承诺；**QA 掌握的是质量信息，不是全部信息**。

因此 QA 在 Go/No-Go 上正确的做法是：

> **不阻拦决策，但确保决策者在知情的前提下做决定，并且这个知情过程留下痕迹。**

这既是职业素养，也是自我保护——出事之后，"当初没人告诉我"是最伤人的一句话。

### 2.3 临近发布发现严重缺陷

不隐瞒、不夸大。第一时间**一次性给出三样东西**：

1. **影响面** —— 多少用户、有无数据损坏、有无资金或合规风险
2. **是否有绕过办法** —— 用户能自救？客服能处理？能用开关关掉？
3. **修复 + 验证需要多久** —— **必须包含验证时间**

然后直接列出三个选项：**延期发布** / **带缺陷发布 + 公告绕过方案** / **关闭该功能后发布**。

> **测试环境全绿不能证明生产可用。**两个环境存在三类系统性差异：**配置不同、数据不同、第三方服务的模式不同**。

### 3.2 观察期（发布后 24 小时）

- [ ] Sentry 错误率处于正常水平
- [ ] 无支付失败率异常
- [ ] 无用户反馈的新增问题

## 4. 回滚预案

发布前必须能回答以下问题，否则不具备发布条件：

| 问题 | 本次答案 |
|---|---|
| 回滚需要多长时间？ | |
| 回滚由谁执行？ | |
| 回滚后，新版本期间产生的数据如何处理？ | |
| 数据库迁移能否回滚？若不能，如何兼容？ | |
| 触发回滚的判断标准是什么？ | |

> **最后一条最容易被忽略。**没有预设标准，回滚决策就会在事故现场靠情绪做出——要么拖太久，要么过早回滚导致数据更混乱。
> 建议的标准示例：核心接口错误率 > 5%，或出现任何资金/权益相关的错误。
