## 什么是回归测试

**回归（Regression）指的是"功能倒退"，不是"回到过去"。**

回归测试回答一个问题：**这次改动有没有弄坏原本好用的东西？**

> ⚠️ **回归（Regression）≠ 回滚（Rollback）**
> - **回归测试**：发布**前**的验证动作，目的是避免需要回滚
> - **回滚**：发布**后**发现问题时的运维补救动作
>
> 两个词中文都带"回"，但完全不相干。

功能之所以会"无故倒退"，是因为代码存在耦合：改 A 影响了 B，而改的人并不知道 B 的存在。**本文档第 2 章就是为了消除这种"不知道"。**

## 1. 每次发布必跑（Core Regression）

无论改动了什么，以下路径都必须验证。**这是产品的生命线。**

### 1.1 自动化部分

```bash
pnpm test          # 全量单元 + 集成测试
pnpm typecheck     # ⚠️ 当前 CI 未包含，必须本地执行
pnpm build         # ⚠️ 当前 CI 未包含，必须本地执行
```

- [ ] 全部测试通过，**无跳过、无重跑**
- [ ] 任何失败都有逐条解释，不接受"重跑一次就好了"
- [ ] `typecheck` 无错误
- [ ] `build` 成功

### 1.2 手工核心路径

| # | 路径 | 关键断言 |
|---|---|---|
| 1 | 游客体验 | 未登录 → 开始 Basic → 10 题 → 交卷 → 出分 |
| 2 | 注册登录 | 验证码注册 → 登录 → 登出 → 再登录 |
| 3 | **完整考试** | 登录 → 开始 → 作答 → 交卷 → 结果 → 错题回顾 |
| 4 | **购买解锁** | 发起购买 → 支付成功 → **权益生效** → 可访问付费内容 |
| 5 | 课程学习 | 打开课时 → 作答检查点 → 标记完成 → 进度更新 |
| 6 | 预约流程 | 查看时段 → 预约 → 收到邮件 → 改期 → 取消 |
| 7 | AI 助手 | 付费用户提问 → 收到基于课程内容的回答 |
| 8 | 双语切换 | EN/ZH 各走一遍路径 1 与 3 |

> 路径 **3** 和 **4** 是绝对不可跳过的两条——一条是产品核心价值，一条涉及真实资金。

## 3. 按变更类型的回归策略

| 变更类型 | 回归范围 |
|---|---|
| 纯文案 / 翻译 | 双语核心路径（1、3）+ 检查无缺失键 |
| 单个页面 UI | 该页面 + 其上下游跳转 |
| 单个 API 逻辑 | 查表 §2 → 该接口 + 其调用方 |
| **权限相关** | **完整权限矩阵**，无例外 |
| **支付相关** | 完整支付链路 + 三张测试卡 + 生产冒烟 |
| 数据模型 | 全量回归 |
| 依赖升级 | 全量回归 + `build` + 手工核心路径 |
| CI / 构建配置 | 全量回归（验证 CI 本身仍能拦住问题） |

## 4. 回归范围的三条决策依据

时间永远不够跑全量，因此"这次该回归哪些"是一项核心判断。三条依据叠加使用：

| # | 依据 | 做法 |
|---|---|---|
| 1 | **变更影响分析** | 查 §2 的映射表，顺依赖链往外推一层 |
| 2 | **缺陷聚集区** | 历史上出过问题的模块，这次多半还会出问题 |
| 3 | **核心业务路径** | 无论改什么，§1.2 的路径 3 与 4 每次必跑 |

> 当三条依据给出的范围不一致时，**取并集**。回归的成本远低于逃逸缺陷的成本。

## 5. Flaky Test 的处理

回归执行中遇到不稳定的测试，**不得简单重跑放行**。

| 步骤 | 动作 |
|---|---|
| 1. 识别 | 同一提交重复执行结果不一致，或"单跑绿、全跑红" |
| 2. 隔离 | 移出必过门禁，**同时建缺陷单跟踪** |
| 3. 归因 | 时间依赖 / **顺序依赖** / **共享状态** / 外部服务 |
| 4. 修复 | 让测试自带前置数据，不依赖执行顺序 |

### 本项目的特定风险

测试套件**共享同一个 Postgres 数据库**、**串行执行**（`fileParallelism: false`）、各文件用 `deleteMany()` 自行清理。

**任一测试未清理干净，下一个测试的失败即为假失败。**识别特征：
- 单独跑通过，全量跑失败
- 改变文件执行顺序，结果就变

遇到这种情况，先怀疑测试数据污染，再怀疑产品代码。
