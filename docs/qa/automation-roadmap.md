> ### ⚠️ 一个容易被"107"这个数字掩盖的事实
>
> **107 个测试文件中，有 34 个（32%）测试的是内部工具**——`remediation` 自动修复 agent 与用户功能无关。
>
> 真正覆盖产品功能（考试、支付、课程、账号、预约、AI 助手）的是 **73 个**。
>
> 这不是说 remediation 的测试没价值，而是提醒：**在评估产品质量覆盖时，应该用 73 而不是 107。**统计口径的差异会直接影响风险判断。

### 1.3 现有测试的优点

在指出缺口之前，先记录做得好的部分——这些是不应在改进中被破坏的：

| 优点 | 价值 |
|---|---|
| **跑真实 Postgres 而非内存库** | 避免了"测试通过但生产报错"的经典陷阱；SQL 方言、约束、事务行为都是真的 |
| **用 pgvector 镜像** | 与生产环境的扩展一致 |
| Route Handler 直接调用 | 不需要启动服务器，速度快且稳定 |
| **`guards.test.ts` 遍历全部后台路由** | 一条用例防住"新增路由忘加鉴权"，写法值得推广 |
| **`chat/route.test.ts` 断言"no LLM call"** | 验证"没有发生什么"，而不只是返回值 |
| `flight-review/book.test.ts` 覆盖完整链路 | 401→403→201→409→取消，是权限测试的范本 |

### 1.5 CI 现状（2026-08-25 更新）

`.github/workflows/test.yml` 现在跑三道门禁：

```yaml
- run: pnpm typecheck   # 最快失败，放最前
- run: pnpm exec vitest run --reporter=json --outputFile=vitest-report.json
- run: pnpm build       # 最慢，放最后
```

补 `build` 的理由：对 Next.js 项目，服务端/客户端边界错误（如在 Server Component 中使用浏览器 API）**只有 `build` 才会发现**，`vitest` 全绿也拦不住。

#### ⚠️ CI 结构上看不见的一类故障

补完门禁后仍有一个**不是靠加测试能解决**的盲点：

`vitest.globalSetup` 会自己补建 `prisma/sql/` 里的部分唯一索引，因此**无论生产是否跑过 `pnpm db:indexes`，CI 都是绿的**。同理，券迁移是一次性数据操作，测试库里根本不存在「没迁移的存量数据」。

这类「环境配置对不对」的问题，测试环境天然无法产生信号 —— 只能靠**对着真实目标库运行的部署门禁**：`pnpm db:verify`（见 [`release-checklist.md`](./release-checklist.md) §1.7.1）与 `/api/health/schema` 冒烟探针。

> 这条经验值得记住：**当一个故障的成因是「测试环境和生产环境不同」时，再多的测试也不会变红。**该做的是把检查搬到生产那一侧去。

## 2. 分阶段路线

### P0 · CI 补齐 —— ✅ **已完成（2026-08-25）**

> 实际落地与下述方案的两点差异：
> - **未加 `--coverage`**。覆盖率的价值在于「找出零覆盖的危险区域」，而不是每次 PR 都算一遍；留到需要时单独跑。
> - **无需注入假环境变量**。实测 `pnpm build` 在完全没有 `.env` 时通过（exit 0）—— 全部路由都是按需服务端渲染，构建期不读运行时配置。
>
> 另补了一项本节写作时还不存在的门禁：`pnpm db:verify`，见 [`release-checklist.md`](./release-checklist.md) §1.7.1。它堵的是 CI **结构上看不见**的一类故障 —— `vitest.globalSetup` 会自己补建部分唯一索引，所以「生产漏跑 `db:indexes`」在 CI 里永远是绿的。

<details>
<summary>原方案（存档）</summary>


**目标**：让类型错误与构建失败无法合入主干。

**动作**：在 `.github/workflows/test.yml` 的 vitest 步骤前后补上：

```yaml
- run: pnpm typecheck
- run: pnpm exec vitest run --coverage --reporter=json --outputFile=vitest-report.json
- run: pnpm build
```

**顺序建议**：`typecheck` 放最前（最快失败），`build` 放最后（最慢）。

**验收标准**：
- [ ] 故意提交一个类型错误的 PR，CI **必须变红**
- [ ] 故意提交一个构建失败的 PR，CI **必须变红**
- [ ] 覆盖率报告可下载，能看出**哪些接口是零覆盖**

**关于覆盖率的正确用法**：
> 重点**不是**追求高百分比数字，而是找出**完全没被测过的危险区域**。
> 58 个 API 路由中，哪些是 0% 覆盖？那才是覆盖率报告的价值。设定"必须达到 80%"这类门槛通常适得其反——它会诱导人写无意义的测试来凑数。

**成本**：约半天，其中大部分时间在处理存量的类型错误（如果有）。

### P1 · 权限矩阵自动化（1~2 天）

**目标**：把 [`permission-matrix.md`](./permission-matrix.md) 中标 ⬜ 的格子变成自动化测试。

**优先补齐**（按风险排序）：

1. **`FR-Only` 身份的全部权限** —— 当前零覆盖，是权限逻辑最易出错的组合
   - TC-EXM-18/19（考试）
   - TC-PAY-20/21/22（课程、AI 助手）
2. **题池难度的接口级验证** —— TC-EXM-20~23
   - 现有测试只断言 `body.total`，从未检查题目内容
3. **权益判定表的 5 种组合** —— TC-PAY-14~18，其中 TC-PAY-16 会暴露 DEF-001

**实现方式**：复用现有的 Route Handler 测试写法，无需新框架。参考 `app/api/exam/routes.test.ts` 的结构。

**验收标准**：
- [ ] 权限矩阵中的每一个 ✅ 都有对应的自动化测试
- [ ] 新增身份或功能时，矩阵与测试同步更新

**为什么排在 E2E 之前**：成本低（复用现有框架）、风险高（权限是安全边界）、且能直接产出可讲的 QA 成果。

### P2 · E2E 覆盖核心旅程（3 天）

**目标**：填补金字塔顶部的空白。

**工具选择**：Playwright（对 Next.js 支持好、内置等待策略、可录制、跨浏览器）。

**只做三条旅程**——不要试图覆盖 35 个页面：

| # | 旅程 | 为什么选它 |
|---|---|---|
| 1 | 注册 → 购买 → 课程解锁 | 涉及资金，且跨越前后端与第三方 |
| 2 | 开始考试 → 作答 → 交卷 → 结果 → 错题回顾 | 产品核心价值，跨越最多页面 |
| 3 | 预约 Flight Review → 取消 → 改期 | 有并发与状态迁移 |

**预期难点**（这些正是 SDET 的日常）：

| 难点 | 应对 |
|---|---|
| 测试数据准备 | 建立数据工厂，每条用例自带前置数据，不依赖执行顺序 |
| Stripe 测试模式打通 | 用 Stripe 测试卡 + Webhook 转发（`stripe listen`） |
| 登录态复用 | Playwright 的 `storageState` 保存登录态，避免每条用例都重新登录 |
| **等待策略** | **从第一天就用语义化等待**（等元素/等网络空闲），绝不用固定 `sleep` |
| 选择器稳定性 | 用 `data-testid` 而非 CSS 类名或文本 |

> ⚠️ **E2E 天生比单测慢且不稳。**从第一天就要认真对待选择器与等待策略，否则很快会变成 flaky 的重灾区，最终被团队忽略——**一套被忽略的 E2E 比没有 E2E 更糟**，因为它消耗维护成本却不提供信号。

**验收标准**：
- [ ] 三条旅程在本地与 CI 均稳定通过
- [ ] 连续运行 10 次，**失败次数为 0**（稳定性验收）
- [ ] 单次全量 E2E 运行时间 < 5 分钟

## 3. 什么该自动化，什么不该

| ✅ 该自动化 | ❌ 不该自动化 |
|---|---|
| 每次发布都要跑的回归路径 | 视觉美观与像素级布局（成本高、误报多） |
| 判分、配额、计费等确定性逻辑 | 一次性的验证 |
| 权限矩阵（组合多、纯机械） | 需求还在频繁变动的功能 |
| 数据一致性校验 | 需要人类判断的（"这个提示够友好吗"） |
| 跨端 / 跨语言的基础流程 | **探索式测试本身** |
| Webhook 幂等等无法手工重现的场景 | **AI 回答的内容质量**（非确定性输出） |

## 4. Flaky Test 治理

### 4.1 本项目的结构性风险

当前测试配置：

```
fileParallelism: false        # 串行执行
共享同一个 Postgres 数据库
各测试文件用 deleteMany() 自行清理
```

**这是顺序依赖的典型温床。**任一测试未清理干净，下一个测试的失败即为**假失败**。

**识别特征**：
- 单独跑通过，全量跑失败
- 改变文件执行顺序，结果就变

**当前尚未痛**，因为测试数量还不算多、且串行执行掩盖了并发问题。但随测试增长，这个成本会快速上升——属于**"现在不痛，痛起来很贵"**的技术债。

### 4.2 改进方向

| 方案 | 说明 | 成本 |
|---|---|---|
| **每条用例自带数据** | 用唯一前缀（如时间戳 + 随机数）构造数据，不依赖全局清理 | 中 |
| 事务回滚隔离 | 每个测试在事务中运行，结束后回滚 | 中 |
| 独立 schema | 每个测试文件用独立 schema，可恢复并行 | 高 |

**建议**：先做第一项。它成本最低，且能立刻消除大部分顺序依赖。

### 4.3 治理流程

| 步骤 | 动作 |
|---|---|
| 1. 识别 | 同一提交重复执行结果不一致 |
| 2. 隔离 | 移出必过门禁，**同时建缺陷单跟踪**——隔离不等于解决 |
| 3. 归因 | 时间依赖 / 顺序依赖 / 共享状态 / 外部服务 |
| 4. 修复 | 让测试自带前置数据、不依赖执行顺序 |

**禁止**：加 retry、加 sleep、直接 skip 删除。

> **唯一允许 retry 的场景**：被测系统本身就允许重试（如真实的网络调用）。用 retry 掩盖测试自身的缺陷，只是把 flaky 变成"暂时不 flaky"。

## 5. 路线小结

| 阶段 | 内容 | 成本 | 收益 |
|:---:|---|:---:|---|
| ~~**P0**~~ | ~~CI 补 `typecheck` + `build`~~ ✅ **已完成 2026-08-25**（另加 `db:verify` 部署门禁） | 半天 | 🔴 **已堵住最大的流程漏洞** |
| **P1** | 权限矩阵自动化（FR-Only、题池分层、权益判定表） | 1~2 天 | 🔴 覆盖最易出错的安全边界 |
| **P2** | Playwright 三条核心旅程 | 3 天 | 🔴 填补金字塔顶部空白 |
| P3 | ESLint / 组件测试 / 性能 | 按需 | 🟠 |

**执行顺序的理由**：P0 成本最低而收益最高，先做；P1 复用现有框架、无需新技术栈，且直接对应最高风险；P2 需要引入新工具与新的稳定性课题，放在有了前两步的基础之后。
