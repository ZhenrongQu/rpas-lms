# 缺陷分级标准与提报规范

| 项 | 内容 |
|---|---|
| 文档版本 | v1.0 |
| 状态 | 生效 |
| 最后更新 | 2026-08-24 |
| 适用范围 | RPAS LMS 全部缺陷 |

> 本文档的作用是建立**共同语言**。没有它，"这个 bug 很严重"是一句主观感受；有了它，严重程度是一个可以被检验的判断。

---

## 1. 两个独立维度

缺陷的紧急程度由两个**互相独立**的维度共同决定。混淆两者是最常见的错误。

| 维度 | 回答什么 | 由谁判定 | 判断依据 |
|---|---|---|---|
| **Severity（严重程度）** | 坏得多厉害 | **QA / 技术** | 数据是否损坏、功能是否可用、是否有安全影响 |
| **Priority（优先级）** | 多急着修 | **PM / 业务** | 影响多少用户、是否影响收入、有无绕过办法、发布窗口 |

**它们经常不一致，而不一致的情况恰恰最需要判断力**（见 §4）。

---

## 2. Severity 分级标准

### S1 · Blocker（阻断）

**判定标准**（满足任一即为 S1）：

- 涉及**资金或权益发放**的任何错误
- 核心流程完全不可用（无法注册、无法登录、无法开始考试、无法交卷）
- **数据损坏或永久丢失**
- 安全边界被突破（答案泄露、越权访问、身份提权）
- 生产环境服务不可用

**本项目的典型 S1**：

| 场景 | 为什么是 S1 |
|---|---|
| 支付成功但权益未发放 | 资金 + 权益 |
| 交卷前正确答案被下发到客户端 | 安全边界，产品核心价值失效 |
| 免费用户能创建 Advanced 考试 | 越权 |
| 客户账号能访问 `/coriander` | 身份提权 |
| 考试作答记录丢失 | 数据丢失 |
| 检查点接口能解析出考试题目答案 | `SEC-04` 隔离失效 |

> **规则**：涉及资金或权益发放的缺陷**一律 S1**，不接受"影响面小"的降级理由。资金问题的信任损失不与影响用户数成正比。

### S2 · Critical（严重）

- 主要功能不可用，但**存在绕过办法**
- 数据显示错误但底层数据正确（如成绩显示错误但存储正确）
- 影响大部分用户的体验阻碍
- 性能严重劣化（核心接口超过 5 秒）

**典型**：考试历史列表不显示（但成绩已正确存储）；某个科目的题目无法抽取到。

### S3 · Major（一般）

- 次要功能异常
- 边界场景下的错误行为
- 错误提示不准确导致用户困惑
- 特定条件下才出现的问题

**典型**：超时后重新进入考试页面显示异常；某语言下的文案缺失；管理后台某个筛选条件失效。

### S4 · Minor（轻微）

- 文案错别字、标点、格式
- 轻微的视觉瑕疵
- 不影响理解的翻译不自然

## 3. Priority 分级标准

| 级别 | 含义 | 处理时限 |
|---|---|---|
| **P0** | 立即处理，可中断当前工作 | 当天 |
| **P1** | 本次发布必须修复 | 发布前 |
| **P2** | 计划在后续迭代修复 | 1~2 个迭代内 |
| **P3** | 有余力时处理 | 不承诺 |

**判定时需要回答的问题**：

1. 影响多少用户？（全部 / 特定身份 / 特定路径 / 极少数）
2. 有无绕过办法？（用户可自救 / 客服可处理 / **完全无解**）
3. 是否涉及收入或法务？
4. 距离发布还有多久？

> **"无绕过办法"应显著提高优先级**——它意味着连客服都帮不了用户。

---

## 4. Severity × Priority 四象限

| | **高 Priority** | **低 Priority** |
|---|---|---|
| **高<br>Severity** | **立即修**<br>例：支付成功但权益未发放。用户付了钱没解锁，资金 + 信任双重损失，且需人工补发历史受影响账号。 | **排期修**<br>例：CMS 某批量操作会丢数据。后果严重，但一年只有管理员用一次且有数据库备份兜底。期间口头告知绕过方式。 |
| **低<br>Severity** | **立即修**<br>例：定价页把 $199 显示成 $19.9。技术上只是文案错误，改一行即可，但直接影响收入且可能构成价格承诺，法务风险高。 | **攒批修**<br>例：FAQ 页中文版错别字。下个迭代一起处理。 |

**记住两个反直觉的格子**：
- 高 Severity + 低 Priority 是**合理的**——严重不等于紧急
- 低 Severity + 高 Priority 也是**合理的**——一个字符的错误可能造成最大的商业损失

## 5. 缺陷单模板

### 5.1 标题公式

```
[模块] 在什么条件下 + 做什么操作 + 出现什么结果
```

| | 示例 |
|---|---|
| ❌ 反例 | 「考试有问题」——无法排期、无法搜索、无法判断严重性 |
| ❌ 反例 | 「交卷失败」——缺条件，无法判断影响面 |
| ✅ 正例 | 「[考试] 免费用户在 difficulty=1 题目不足时创建 Basic 考试，收到题量少于 35 题的试卷且无任何提示」 |

### 5.2 完整模板

```markdown
## 标题
[模块] 条件 + 操作 + 结果

## 分级
Severity：S1 / S2 / S3 / S4
Priority：待分诊会确认（由 PM 判定）
复现率：N / M（见 §6）

## 环境
版本 / 分支 / 提交：
客户端：Chrome 129 / iOS 原生 / ...
账号类型：GUEST / FREE / PAID / FR-Only / ADMIN
界面语言：EN / ZH

## 前置条件
（执行步骤前必须成立的状态）

## 复现步骤
1.
2.
3.

## 预期结果
（引用 PRD 编号，如 R-EXM-03；若 PRD 未定义则明确写"PRD 未定义"）

## 实际结果

## 影响面
- 影响哪些用户、多大比例
- 是否有数据损坏或丢失
- 是否涉及资金 / 安全 / 合规

## 绕过办法
（用户可自救 / 客服可处理 / 无）

## 证据
截图、录屏、日志片段、Sentry 事件 ID、数据库记录

## 备注
（关联的需求编号、用例编号、相似缺陷）
```

### 5.3 为什么"影响面"和"绕过办法"是关键

新手写的缺陷单常被无视，原因几乎总是同一个：**只写了怎么复现，没写为什么值得修**。

开发和 PM 每天面对几十个单子，决定先看哪个靠的是**影响面**，不是步骤的详细程度。而"无绕过办法"这一句，往往是把 P2 推到 P1 的决定性因素。

## 6. 复现率规范

### 6.1 记录方式

**必须写成分数，不写百分比。**

| | |
|---|---|
| ✅ `5 / 10` | 传达了样本量 |
| ❌ `50%` | `1/2` 和 `50/100` 都是 50%，可信度天差地别 |

### 6.2 必须定义"一次尝试"

同一个缺陷，"重复完整步骤一次"和"在页面上刷新一次"是完全不同的尝试单位，得出的复现率没有可比性。**缺陷单中必须写明**。

### 6.3 复现率影响什么

| 影响 | 说明 |
|---|---|
| ✅ 影响 **Priority** | 高频问题更急 |
| ✅ 影响**排查策略** | 高复现率直接调试；低复现率走埋点路线 |
| ❌ **不影响 Severity** | 1/10 的资金缺陷依然是 S1——严重程度不因罕见而降低 |

### 6.4 低复现率的排查提示

**复现率低通常意味着存在时序或并发因素。**

实用技巧：换一种触发方式再试。若用脚本快速连续触发后复现率从 3/20 跳到 10/10，说明隐藏变量已被找到——这本身就是一种定位手段，比反复手工重试有效得多。

## 7. 缺陷生命周期

```
NEW ──► TRIAGED ──► ASSIGNED ──► FIXED ──► VERIFIED ──► CLOSED
         │              │                      │
         │              │                      └─(验证不通过)─► REOPENED ──┐
         │              │                                                  │
         │              └─────────────────◄─────────────────────────────────┘
         │
         ├──► REJECTED（Not a Bug / Duplicate / Won't Fix）
         └──► CANNOT REPRODUCE（见 §8.1）
```

**QA 在这条链上出现三次**：提单（NEW）、跟进分诊（TRIAGED）、**验证修复（VERIFIED）**。

> 第三次最容易被跳过。**开发说"修好了"不等于修好了**——必须由 QA 在与缺陷单相同的环境和步骤下确认。

### 7.1 缺陷回流（Closing the Loop）

缺陷关闭时还有最后一个动作，也是长期价值最高的一个：

> **每个逃逸到生产的缺陷，都应该在测试套件里留下一道疤。**

具体做法：
1. 补一条自动化用例，锁死这个行为
2. 更新回归清单
3. 简短复盘：**为什么之前的用例没抓到它？**——答案往往会揭示用例设计的系统性盲区

## 8. 特殊情况处理

### 8.1 无法稳定复现

**不要直接标 Cannot Reproduce 关单。**"无法复现"本身是信息——它说明存在尚未识别的隐藏变量。

**处理路径**：

1. 列出候选变量，二分法逐个固定：
   - 时间与时区、数据状态（新账号 vs 有历史数据）
   - 账号类型与权限、缓存（浏览器 / CDN / 服务端）
   - 并发、网络（弱网、超时重试）
   - 客户端（浏览器版本、扩展、屏幕尺寸、语言）
2. 寻找**非复现类证据**：服务端日志、Sentry 事件、数据库异常记录
3. **只要证据能证明它发生过，缺陷单就成立**，不必非要在自己手上复现
4. 证据确实不足时，转为"待观察"并推动加埋点，**而非关闭**

### 8.2 开发认为"这不是 bug，是设计如此"

先分清三种情况，处理方式完全不同：

| 情况 | 处理 |
|---|---|
| **(a) QA 误解了需求** | 承认并关单。但要追问：为什么会误解？若因需求含糊，顺手提一个**需求缺陷** |
| **(b) 需求确实这么写，但设计有问题** | 不要和开发争——开发只是按需求实现。转成产品改进建议交 PM |
| **(c) 需求根本没写，双方都在猜** | 这是**需求缺陷**，拉 PM 定论。本项目的 PRD 未定事项大多属于此类 |

> **核心心法：QA 不需要赢得争论，只需要让有权决定的人做出明确决定，并且这个决定留下痕迹。**
> 争赢一个开发不产生价值；一个没被记录的口头结论，三个月后会变成新的争论。

### 8.3 临近发布发现严重缺陷

不隐瞒、不夸大。第一时间**一次性给出三样东西**：

1. **影响面** —— 多少用户、有无数据损坏、有无资金或合规风险
2. **是否有绕过办法** —— 用户能自救吗？客服能处理吗？能用开关关掉吗？
3. **修复 + 验证需要多久** —— **必须包含验证时间**，不只是开发时间

然后直接列出通常的三个选项：**延期发布** / **带缺陷发布 + 公告绕过方案** / **关闭该功能后发布**。

## 9. 本项目的已知缺陷（首批）

以下三项来自 PRD 编写过程中的代码审查，**在任何测试执行之前就已确认存在**：

| ID | 标题 | Severity | 状态 | 修复方向（PO 已决策） |
|---|---|:---:|---|---|
| DEF-001 | [支付] `paid_access` 权益无任何撤销路径，退款后课程权限无法收回 | **S1** | **已定方案·待修复** | 补齐 `revokePaidAccessEntitlement`，**与 `accessTier` 重置同事务**；新增退款申请审核流程（PRD U5 / R-PAY-05） |
| DEF-002 | [考试] 服务端不校验考试超时，客户端未运行时超时会话永久悬挂且作答丢失 | **S2** | **已定方案·待修复** | 服务端惰性结算：读取会话时发现超时未交卷即自动判分落库（PRD U2 / R-EXM-07） |
| DEF-003 | [考试] 题池不足时静默生成题量不完整的试卷，无任何提示 | **S2** | **已定方案·待修复** | 创建前校验题池充足性，不足则拒绝创建；CMS 增加题库健康度告警（PRD U1） |

> **DEF-001 之所以是 S1**：涉及资金与权益，且**无绕过办法**（只能手工改数据库）。按本文档 §2 的规则，涉及资金或权益发放的缺陷一律 S1。
>
> **DEF-003 的危害容易被低估**：因为及格线按**实际题量**计算（`score.ts:39-45`），一份 20 题的试卷答对 13 题即判「通过」。用户会得到一个**虚假的通过信号**——这比考试无法开始有害得多。
