## 1. 账号与身份（R-ACC）

**风险等级**：🟠 中高 — 安全关键，但逻辑相对标准

### 测试重点

| 重点 | 关键断言 | 方法 |
|---|---|:---:|
| **验证码边界** | 有效期 **10 分钟**：9分59秒有效、10分01秒失效 | BVA |
| **验证码尝试上限** | 第 5 次错误后该码**永久失效**，即使随后输入正确码 | BVA |
| **验证码并发消费** | 同一码被两个请求同时验证，**只有一个成功** | EG |
| **客户登录锁定** | 8 次失败后锁定 15 分钟；**第 9 次即使密码正确也拒绝** | BVA |
| **管理员登录锁定** | 5 次失败后锁定 **30 分钟** | BVA |
| **锁定的双维度** | 账号锁定后**换 IP 仍被拒**；IP 锁定后**换账号也受限** | DT |
| **MFA 计入失败** | 密码正确但 TOTP 错误，**失败计数 +1** | ST |
| **MFA 强制性** | 已开启 MFA 时，仅密码**不足以登录** | DT |
| **账号复用** | 邮箱注册后用同一邮箱 OAuth 登录，**复用同一 Customer** | EG |
| **OAuth 降级** | 未配置凭据时，登录页**不显示**对应按钮 | — |
| **双表隔离** | 客户账号登录 `/coriander` 失败；无任何字段可提权 | DT |

已有单元测试：`verificationCode.test.ts`、`totp.test.ts`、`adminMfa.test.ts`、`adminGuard.test.ts`、`weakPassword.test.ts`、`localAccount.test.ts`、`oauthConfig.test.ts`。覆盖较好。

### 缺口

- ⬜ **锁定的时间边界**（锁定期满后能否正常登录）无覆盖

## 3. 课时检查点（R-CKP）

**风险等级**：🟠 中高 — **逻辑简单但安全隔离必须验证**

### 测试重点

| 重点 | 关键断言 | 方法 | 优先级 |
|---|---|:---:|:---:|
| **`SEC-04` 隔离** ⭐ | 用**考试题 ID** 调用检查点接口 → **404**，绝不返回答案 | EG | **P0** |
| 公开可用 | 未登录用户可正常作答 | DT | P0 |
| 即时反馈 | 返回对错、正确选项 ID、对应语言的解析 | — | P0 |
| **IP 限流** | 60 秒内第 121 次请求 → **429 + `Retry-After`** | BVA | P1 |
| 限流解除 | 封禁 60 秒后恢复正常 | BVA | P2 |
| 不存在的题目 ID | 404，不泄露任何信息 | EG | P1 |
| 双端一致 | 移动端检查点接口行为与 Web 一致 | PW | P1 |

### 为什么隔离验证是 P0

检查点是**公开、无需登录**的接口。如果它能解析考试题目 ID，全部考试答案立刻泄露——**产品的核心价值（模拟考试的真实性）当场归零**。

当前用**物理表隔离**（`CheckpointQuestion` 独立于两个考试题库）而非权限判断来保证。这是更强的保证方式：权限判断可能写错，物理隔离不会。但仍需用例锁定，防止将来有人"为了复用代码"把两个查询合并。

### 现有覆盖

`app/api/checkpoint/checkpoint.test.ts`（4 处状态码断言）、`app/api/mobile/checkpoint/routes.test.ts`（3 处）。核心隔离已覆盖。

### 缺口

- ⬜ 限流阈值的边界验证（120 / 121）

## 4. Flight Review 预约（R-FRV）

> ⚠️ **本节描述的是改造前的现状。**
> U13 决策将 Flight Review 改为**一次性消耗品**（PRD N15），涉及新增审查券、移除 `customerId @unique`、引入状态机与数据迁移。
> **改造后的完整用例见 [`flight-review.md`](./flight-review.md)（52 条）**——那是当前待办中风险最高的一块。

**风险等级**：🟠 中高（改造后）— 并发场景与券状态机是重点

### 测试重点

| 重点 | 关键断言 | 方法 |
|---|---|:---:|
| **资格判定** | PAID **或** 持 flight_review 权益 → 可预约；纯 FREE → 403 | DT |
| **并发抢占** ⭐ | 两用户同时预约同一时段，**只有一个成功**，另一个收到 409 | EG |
| **一人一约** | 已有预约的用户预约新时段 → 视为**改期**，原时段释放 | ST |
| 取消 | 取消后时段重新可被预约 | ST |
| 越权取消 | 用户 A 取消用户 B 的预约 → 拒绝 | DT |
| 过期时段 | 预约已过去的时段 → 应拒绝（**需确认是否实现**） | EG |
| 通知邮件 | 预约/改期/取消各触发对应邮件，内容按语言本地化 | PW |
| **邮件失败** | 邮件发送失败时**预约仍然成功**（U12 决策），失败被记录 | EG |
| **重发入口** | 用户端与管理端各有重发入口，且有频率限制 | EG |
| **详情页自足** | 不打开邮箱也能看到完整的时间、地点、评审员信息 | — |
| 事务边界 | 邮件发送在预约事务**之外**——邮件服务超时不得拖长或回滚事务 | EG |

### 并发抢占为什么值得单独测

数据库的 `slotId @unique` 约束在**数据层**杜绝了重复预约——这是比应用层加锁更强的保证。但需要用例确认两件事：

1. 约束确实生效（第二个请求失败）
2. **失败被优雅处理**（返回 409 而不是抛出未捕获的数据库异常导致 500）

第 2 点是实际的风险：约束生效了，但用户看到的是一个 500 错误页。

### 现有覆盖

`app/api/flight-review/book.test.ts` 覆盖了完整链路：401 → 403 → 201 → **409 抢占** → 取消释放。**这是本项目权限测试写得最完整的模块**，可作为其他模块的范本。

`notifications.test.ts` 覆盖了邮件内容与 HTML 转义。

### 缺口

- ⬜ 越权取消他人预约
- ⬜ 过期时段的预约行为
- ⬜ 邮件发送失败时预约仍成功（U12 已决策，待实现）
- ⬜ 重发入口与频率限制（U12 新增能力）
- ⚠️ **FR-Only 用户重复购买的处理待澄清**（PRD U13）——当前 `customerId @unique` 使一个学员只能有一个预约，重复购买不产生额外权利

## 5. AI 学习助手（R-AIA）

**风险等级**：🟡 中 — 门禁必须验证，回答质量不做断言

### 测试重点

| 重点 | 关键断言 | 方法 | 优先级 |
|---|---|:---:|:---:|
| **门禁顺序** ⭐ | 401 → 402 → 429 → 503，**顺序不可调换** | ST | **P0** |
| **鉴权前不计费** ⭐ | 未登录/未付费请求**不产生任何模型调用** | EG | **P0** |
| FR-Only 用户 | → **402**（购买实操审查不含 AI 助手） | DT | P0 |
| **速率限制** | 60 秒内第 21 次请求 → 429 + `Retry-After` | BVA | P1 |
| 未配置 API Key | 付费用户 → 503，**其余功能不受影响** | EG | P0 |
| 范围限制 | 与 RPAS 无关的提问被拒绝，**且不进入模型循环** | EP | P1 |
| 输入校验 | 畸形 body、最后一条消息非用户发出 → 400 | EP | P1 |

### 门禁顺序为什么本身就是安全属性

若顺序被调换——例如先检查 API Key 再检查付费——会产生两个问题：

1. 未付费用户能通过错误码差异**探测系统状态**
2. 更严重的是，**可能在鉴权完成前就消耗了模型调用成本**

`chat/route.test.ts` 中有一条用例名为 `paid user passes all gates and stops at the missing key (503, no LLM call)`——**测试名里的 "no LLM call" 是这条用例的灵魂**。它验证的不是返回值，而是"没有发生什么"。

### 不测什么

**AI 回答的内容质量不在本用例集范围内。**非确定性输出无法用断言验证，强行断言只会产生 flaky test。该部分由 `scripts/eval/` 的 LLM 评审机制单独处理（`pnpm eval:assistant`）。

### 现有覆盖

`app/api/chat/route.test.ts`（401 / 402 / 400 / 503 + no-LLM-call）、`scopeGate.test.ts`、`retrieve.test.ts`、`ingest.test.ts`、`tools.test.ts`。

### 缺口

- ⬜ 速率限制阈值（20 / 21）未验证 —— **成本相关，建议补齐**
- ⬜ FR-Only 用户的 402

## 6. 管理后台 CMS（R-CMS）

**风险等级**：🟢 低 — 内部工具，用户面小

### 测试重点

| 重点 | 关键断言 | 方法 |
|---|---|:---:|
| **全路由鉴权** ⭐ | 非管理员访问**任何** `/coriander` 接口 → **404**（非 403） | DT |
| 题目状态 | 仅 `ACTIVE` 状态的题目进入考试抽取 | DT |
| 快照不受影响 | 修改/下架题目**不影响进行中的考试**（见 exam.md 第 6 组） | EG |
| 输入校验 | 畸形请求体 → 422 | EP |
| 权益操作 | 授予幂等；对已撤销权益授予会**取消撤销标记** | ST |
| 时段管理 | 发布、修改、删除时段；**删除已被预约的时段**的行为需确认 | EG |

### 404 而非 403 是有意设计

403 会确认"这个路径存在但你没权限"，等于向探测者确认了后台路径。404 则不泄露存在性。

`guards.test.ts` 的 `returns 404 for a non-admin on every coriander route` **用一条用例遍历了所有后台路由**——这是防止"新增路由时忘记加鉴权"的好写法，值得在其他模块复用。

### 缺口

- ⬜ 删除已被预约的 Flight Review 时段会发生什么（需求未定义）
- 🟡 权益授予/撤销的接口级验证不足

## 7. 移动端 API（R-MOB）— 横切风险

**风险等级**：🟠 中高 — **行为漂移风险最高**

### 核心风险

`app/api/mobile/*` 是一套与 Web **并行的独立实现**。这意味着同一条业务规则存在两处代码，**一处被修改而另一处遗漏**的风险是持续存在的。

这类缺陷的特征是**极难发现**：Web 端测试全绿、功能验收通过、用户报告"手机上不一样"，而没有人能立刻说出哪里不一样。

### 强制双端验证的规则

以下规则的用例**必须在 Web 与移动端各执行一次**：

| 规则 | 需求编号 | Web 覆盖 | 移动端覆盖 |
|---|---|:---:|:---:|
| 三层题池分层 | R-EXM-03 | 🟡 单测 | ⬜ |
| 交卷前不下发答案 | R-EXM-05 | 🟡 | ✅ |
| 考试会话所有权 | R-EXM-10 | ✅ | ✅ |
| 创建 Advanced 的权限 | R-EXM-03 | ✅ | ✅ |
| 课时访问权限 | R-LRN-03 | ✅ | ✅ |
| 判分规则 | R-EXM-06 | ✅ | 🟡 共用引擎 |

### 移动端特有的测试重点

| 重点 | 关键断言 | 方法 |
|---|---|:---:|
| **令牌哈希存储** | 数据库中**不存在明文令牌** | EG |
| **令牌有效期** | 30 天边界：第 29 天有效、第 31 天失效 | BVA |
| **令牌撤销** | 登出后原令牌立即失效 | ST |
| 缺失/畸形 Authorization 头 | 401 | EP |
| **不接受 Cookie 鉴权** | 携带有效 Web Cookie 但无 Bearer Token → **401** | EG |

> 最后一条容易被忽略但很重要：两套鉴权体系必须**互不串用**。若移动端接口意外接受了 Cookie，就等于在移动端 API 上开了一个未经设计的入口。

### 现有覆盖

移动端测试相当完整：`mobile/exam/routes.test.ts`（7 处状态码断言）、`mobile/lessons`（8 处）、`mobile/checkpoint`（3 处）、`mobile/auth`（3 处）、`mobile/account`（3 处）、`mobile/flight-review`（2 处）。

**移动端的接口级权限覆盖实际上优于 Web 端。**

### 缺口

- ⬜ 移动端的题池难度分层（与 Web 同为缺口）
- ⬜ 令牌有效期边界
- ⬜ Cookie 不可用于移动端鉴权

三项缺口横跨多个模块，建议**集中补齐**而非分散处理：

1. **`FR-Only` 身份** —— 在考试、课程、AI 助手三个模块均无覆盖

3. **时间边界** —— 考试超时、验证码 10 分钟、令牌 30 天、锁定期满，均未验证
