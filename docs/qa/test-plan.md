## 1. 测试目标

本计划要回答三个问题：**测什么、怎么测、测到什么程度算完**。

具体目标按优先级排列：

1. **保证付费与权益的正确性** —— 涉及真实资金，任何缺陷都直接造成收入损失或用户信任损失
2. **保证考试判分与题池隔离的正确性** —— 这是产品的核心价值，判分错误会给用户错误的备考信号
3. **保证权限边界不被突破** —— 免费用户不得触达付费内容，答案不得在交卷前泄露
4. **暴露 PRD 第 10 章的 12 项未定义行为** —— 用例的作用不只是验证已知规则，也包括**把没人做过决策的地方逼出来**
5. **建立可重复、可交接的测试资产** —— 使测试不依赖任何特定个人的记忆

## 2. 测试范围

### 2.1 在范围内（In Scope）

| # | 功能域 | 测试深度 | 理由 |
|---|---|---|---|
| 1 | 模拟考试 | **详尽**（用例级） | 核心价值，逻辑最复杂 |
| 2 | 支付与权益 | **详尽**（用例级） | 涉及资金，风险最高 |
| 3 | 账号与身份 | 中等 | 安全关键但逻辑相对标准 |
| 4 | 课程与课时 | 中等 | 权限边界需重点验证 |
| 5 | Flight Review 预约 | 中等 | 并发场景需重点验证 |
| 6 | 课时检查点 | 轻量 | 逻辑简单，但**安全隔离必须验证** |
| 7 | AI 学习助手 | 轻量 | 门禁顺序必须验证，回答质量不做断言 |
| 8 | 管理后台 CMS | 轻量 | 内部工具，用户面小 |
| 9 | 移动端 API | **中等偏重** | 与 Web 并行实现，**行为漂移风险高** |

### 2.2 不在范围内（Out of Scope）

| 不测 | 理由 |
|---|---|
| AI 助手回答的**内容质量** | 非确定性输出，无法用断言验证；由 `scripts/eval/` 的 LLM 评审单独处理 |
| 视觉还原度与像素级布局 | 自动化成本高、误报率高，收益低 |
| 性能与负载 | 当前用户规模下不划算，列入后续（见 §9） |
| 第三方服务自身的可用性 | Stripe / Resend / Cloudflare 的 SLA 不由本产品保证 |
| 渗透测试 | 需专业安全团队，非本计划覆盖范围 |
| 无障碍（a11y）合规审计 | 有价值但需专项投入，列入后续 |

## 3. 质量风险评估

风险 = **影响** × **发生概率**。这张表决定了后续所有资源分配。

| ID | 风险 | 影响 | 概率 | 等级 | 缓解措施 |
|---|---|---|:---:|:---:|---|
| RSK-01 | 支付成功但权益未发放 | 极高 | 中 | 🔴 | Webhook 幂等用例 + 生产冒烟必测 |
| RSK-02 | **课程权益无法撤销**（退款无解） | 极高 | **已发生** | 🔴 | 见 PRD U5；本计划纳入 TC-PAY-11~13 验证 |
| RSK-03 | 免费用户拿到题量不足的试卷 | 高 | 中 | 🔴 | TC-EXM-30~32；同时推动 PRD U1 决策 |
| RSK-04 | 超时会话永久悬挂，作答丢失 | 高 | **必然发生** | 🔴 | TC-EXM-24~27；推动 PRD U2 决策 |
| RSK-05 | 交卷前答案泄露 | 极高 | 低 | 🟠 | 全接口横向验证（含移动端） |
| RSK-06 | 权限越界（免费触达付费内容） | 高 | 中 | 🟠 | 权限矩阵全量验证 |
| RSK-07 | **移动端与 Web 行为漂移** | 高 | 高 | 🟠 | 关键规则双端对照验证 |
| RSK-08 | 类型错误 / 构建失败合入主干 | 中 | **高** | 🟠 | CI 补齐（自动化路线 P0） |
| RSK-09 | 判分逻辑错误 | 高 | 低 | 🟡 | 已有较好单测覆盖，补边界用例 |
| RSK-10 | 预约并发导致重复占用 | 中 | 低 | 🟡 | 数据库唯一索引已保证，补验证用例 |
| RSK-11 | Flaky test 污染 CI 信号 | 中 | 中 | 🟡 | 见 §7.3 |
| RSK-12 | 双语文案缺失 | 低 | 中 | 🟡 | 纳入发布准入检查 |
| **RSK-13** | **移除 `customerId @unique` 后，「一人一约」由 DB 保证降级为应用层判断** | 高 | 中 | 🔴 | 并发用例 TC-FRV-36；建议改用**部分唯一索引**把约束拉回 DB 层 |
| **RSK-14** | **FR 消耗品迁移出错，已付费用户失去预约资格** | 极高 | 中 | 🔴 | TC-FRV-41/42；生产数据副本演练 + 迁移前后资格总量比对 |
| **RSK-15** | 重复取消可重复退券 → 刷出无限张券（资损） | 高 | 低 | 🟠 | TC-FRV-27 |

> **RSK-02 与 RSK-04 的"概率"栏值得注意**：它们不是"可能发生"，而是**已经存在于当前代码中**。这类风险不需要测试去"发现"，需要的是推动决策与修复。

## 4. 测试策略

### 4.1 分层策略

| 层级 | 职责 | 当前状态 | 目标 |
|---|---|---|---|
| **单元测试** | 纯逻辑：判分、配额、权限判定、格式化 | ✅ 约 82 个文件，覆盖良好 | 维持 |
| **集成测试**（Route Handler） | 接口契约：状态码、权限、数据落库 | ✅ 约 25 个文件 | 补齐零覆盖接口 |
| **端到端测试** | 跨页面的真实用户旅程 | ⬜ **完全缺失** | 3 条核心旅程 |
| **手工探索式测试** | 发现未知风险 | ⬜ 无组织 | 每迭代 1~2 个 charter |
| **手工验收测试** | 发布前核心路径确认 | ⬜ 无清单 | 见发布准入清单 |

> 详细路线见 [`automation-roadmap.md`](./automation-roadmap.md)。

### 4.3 用例设计方法

所有用例必须标注其设计方法，便于评审时判断覆盖是否充分：

| 方法 | 缩写 | 主要应用 |
|---|---|---|
| 等价类划分 | `EP` | 判分、输入校验 |
| 边界值分析 | `BVA` | 题量、及格线、时限、限流阈值 |
| 判定表 | `DT` | 多条件组合的权限判定 |

## 5. 测试环境与数据

### 5.1 环境要求

| 环境 | 用途 | 数据 |
|---|---|---|
| 本地开发 | 单元 / 集成测试 | Docker Postgres（**必须用 `pgvector/pgvector:pg16` 镜像**，非标准 postgres 镜像——`KnowledgeChunk` 表含 vector 列） |
| CI | 每次 PR 自动执行 | 同上，GitHub Actions service container |
| 预发布 | 手工验收、E2E | 需独立数据库与 Stripe 测试模式 |
| 生产 | 发布后冒烟 | 真实数据，**只做只读验证与一笔真实小额支付** |

### 5.2 测试数据要求

| 数据 | 用途 | 当前状态 |
|---|---|---|
| 各难度的 Basic 题目（0 / 1 / 其他） | 验证三层题池 | 需确认题库中 difficulty 分布 |
| **difficulty=1 题目 ≥ 35 道** | 验证 FREE 用户完整试卷 | ⚠️ **必须先确认**，直接关系 RSK-03 |
| 5 种身份的测试账号 | 权限矩阵验证 | 需建立并固定 |
| Stripe 测试卡（成功/失败/3DS） | 支付路径验证 | Stripe 官方提供 |
| 双语齐全 / 仅单语的课时 | 验证 i18n 降级 | 需构造 |

### 5.3 已知的环境风险

测试套件当前**共享同一个 Postgres 数据库**、**串行执行**（`fileParallelism: false`）、各测试文件用 `deleteMany()` 自行清理。

**这构成顺序依赖风险**：任一测试未清理干净，下一个测试的失败即为**假失败**。识别特征是「单独跑通过、全量跑失败」或「改变执行顺序结果就变」。见 §7.3。

## 6. 进入与退出准则

### 6.1 测试进入准则（Entry Criteria）

满足以下条件才开始正式测试，否则打回：

- [ ] 需求已明确（对应 PRD 中的编号需求，或已在评审中澄清）
- [ ] 代码已合入待测分支，`pnpm build` 可通过
- [ ] 冒烟测试通过（核心路径可走通）
- [ ] 测试环境可用，测试数据已就绪
- [ ] 开发已完成自测并说明本次改动的影响范围

> **冒烟不过直接打回，不进入深度测试。**这不是刁难，是避免在明显不可用的版本上浪费整轮测试时间。

### 6.2 测试退出准则（Exit Criteria）

- [ ] 计划内的用例执行完毕，执行率 ≥ 95%
- [ ] 用例通过率 ≥ 95%
- [ ] **P0 / P1 缺陷全部关闭并经 QA 验证**
- [ ] 遗留的 P2 / P3 缺陷已逐条列出，**并由 PM 明确接受**（留痕）
- [ ] 全量自动化回归通过；任何失败都有逐条解释（不接受"重跑就好了"）
- [ ] 回归清单执行完毕
- [ ] 测试报告已产出

## 7. 特殊事项

### 7.1 关于 PRD 未定事项的处理

PRD 第 10 章列出 12 项未定义行为。QA 的处理原则是：

> **对未定义行为，用例断言"当前实际行为"，并标注 `⚠️ 待 PO 决策`。**

理由：未定义不等于可以不测。记录当前行为可以确保它**不会在无人察觉的情况下改变**；而 `待决策` 标记则保证决策做出后，用例会被同步更新。

### 7.2 关于两套并行实现

`app/api/mobile/*` 是与 Web 并行的独立实现。**凡涉及以下规则的用例，必须双端各执行一次**：

- 三层题池（R-EXM-03）
- 答案不下发（R-EXM-05）
- 课时访问权限（R-LRN-03）
- 判分规则（R-EXM-06）

### 7.3 Flaky Test 治理规则

| 步骤 | 动作 |
|---|---|
| 1. 识别 | 同一提交下重复执行结果不一致，或"单跑绿、全跑红" |
| 2. 隔离 | 移出必过门禁，**同时建缺陷单跟踪**——隔离不等于解决 |
| 3. 归因 | 四类：时间依赖 / 顺序依赖 / 共享状态 / 外部服务 |
| 4. 修复 | 让测试自带前置数据、不依赖执行顺序 |

**禁止的做法**：加 retry、加 sleep、直接 skip 删除。前两者掩盖问题，后者连同它保护的功能一起丢弃。

**唯一允许 retry 的场景**：被测系统本身就允许重试（如真实网络调用）。

### 7.4 假失败的统计

测试失败必须归类为三种之一，**并分开统计**：

| 类别 | 含义 | 处理 |
|---|---|---|
| 产品缺陷 | 被测代码有问题 | 提缺陷单 |
| 测试缺陷 | 用例本身写错了 | 修用例，不提缺陷单 |
| 环境缺陷 | 数据脏了、服务没起来 | 修环境，记录以便改进 |

**假失败率（后两类占比）超过 20% 应触发专项治理**——它比漏测更危险，因为它会训练团队忽略红色信号。

## 8. 角色与职责

本项目由单人承担多角色，但职责边界仍需清晰，否则会出现"自己批准自己"的盲区：

| 角色 | 职责 | 关键约束 |
|---|---|---|
| PO / PM | 决策 PRD 未定事项、确定 Priority、接受遗留风险 | 决策需留痕 |
| 开发 | 实现、单元测试、修复缺陷 | 不自行判定缺陷是否成立 |
| QA | 用例设计、执行、缺陷提报、**验证修复**、发布准入结论 | **修复必须由 QA 验证，开发说"修好了"不算** |
| SDET | 测试框架、CI、测试数据、flaky 治理 | — |

> **单人项目的最大风险是角色混淆**。缓解方式：切换角色时明确声明当前立场（"我现在以 QA 身份判断这个能不能发"），并把结论写进文档而非停留在脑子里。
