## 为什么需要探索式测试

用例集只能验证**已经想到的**风险。而行业经验一致指向一个事实：**大部分严重缺陷是探索式测试发现的，不是脚本化用例发现的**——因为脚本化用例本质上是"把已知的答案再确认一遍"。

探索式测试不是"随便点点"。它有四个要素，缺一不可：

| 要素 | 说明 |
|---|---|
| **Charter（章程）** | 一两句话写明本次探索的目标与边界 |
| **时间盒** | 60~120 分钟，期间**不被打断、不做别的事** |
| **记录** | 过程中随手记：做了什么、发现什么、产生什么疑问 |
| **Debrief（复盘）** | 结束后回顾，决定下一个 charter |

时间盒和记录的意义在于让探索式测试**可管理、可汇报、可计入工时**，而不是看起来像在划水。

---

## 通用记录模板

```markdown
## Charter: <名称>
执行人：          日期：
时间盒：90 分钟   实际用时：

### 覆盖了什么
（实际测试的路径，与计划的差异）

### 发现（Findings）
- F1:
- F2:

### 缺陷（Bugs）
- 已提单：DEF-xxx

### 疑问（Questions）
- Q1: （需要 PO / 开发回答的问题）

### 下一步
（建议的下一个 charter，或需要补充的用例）

### 时间分配
测试 __% / 环境与数据准备 __% / 排查与记录 __%
```

> 最后一项"时间分配"是 SBTM 的标准要求。若准备时间长期超过 40%，说明测试数据或环境需要专项改进——这是一个**可量化的改进信号**。

## CH-01 · 考试会话在异常中断下的行为

| 项 | 内容 |
|---|---|
| **目标** | 找出考试流程在非正常路径下的状态异常与数据丢失 |
| **时间盒** | 90 分钟 |
| **范围** | `/exam` 创建 → 答题 → 交卷 → 结果 → 回顾 全流程 |
| **不含** | 支付、CMS、AI 助手 |
| **优先级** | **P0** — 覆盖两项已知高风险未定义行为 |

### 测试思路（边测边补充）

1. 答到一半直接关闭浏览器，重新打开考试 URL
2. 答到一半退出登录，重新登录后回到考试
3. **同一场考试在两个标签页同时打开，交替作答**
4. 点交卷的瞬间断网，恢复后刷新
5. 交卷成功后按浏览器后退键，再点一次提交
6. 直接访问 `/exam/{把 id 改成别人的}/review`
7. **计时到点但不做任何操作，放置 5 分钟**
8. 中途把界面语言从 EN 切到 ZH
9. 交卷后修改 URL 中的 sessionId 查看他人结果
10. 在移动端开始考试，在 Web 端继续

### 已知的高风险方向

> 第 **3**、**5**、**6**、**7** 条最可能出问题：
> - **第 7 条**直接对应 PRD U2（超时会话永久悬挂）——预期会复现该问题
> - **第 3 条**（双标签页并发）的行为完全未定义，答案可能互相覆盖
> - **第 6 条**对应 `requireExamOwner`，但**游客的无主会话是一个独立分支**，值得单独试
> - **第 5 条**代码层已实现幂等，本次是验证它在真实浏览器行为下是否成立

### 探索启发法

用 **SFDIPOT** 逐维度追问"这里能怎么坏"：
Structure（结构）· Function（功能）· **Data（数据）** · Interface（接口）· **Platform（平台）** · Operations（操作）· **Time（时间）**

本 charter 重点在 **Data / Time / Platform** 三个维度。

## CH-02 · 权限边界与身份组合越权探测

| 项 | 内容 |
|---|---|
| **目标** | 找出权限判断在非典型身份组合下的漏洞 |
| **时间盒** | 90 分钟 |
| **范围** | 全部需要身份判断的接口 |
| **不含** | 管理后台的内部功能细节 |
| **优先级** | **P0** — `FR-Only` 身份当前零覆盖 |

### 准备工作

预先建好 5 个账号，**这是本 charter 成功的前提**：

| 账号 | 状态 |
|---|---|
| A | 未登录（浏览器隐身窗口） |
| B | FREE，无任何权益 |
| C | PAID（持 `paid_access`） |
| D | **FR-Only**：`accessTier = FREE` + 持 `flight_review` 权益 |
| E | ADMIN |

### 测试思路

1. **用 D 账号把 C 能做的事全试一遍** —— 考试、课程、AI 助手，预期全部拒绝，只有预约放行
2. 用 B 账号直接访问 PAID 课时的 URL（不通过导航）
3. 用 B 账号直接 POST 创建 Advanced 考试（绕过前端按钮）
4. 用 C 账号访问 `/coriander` 及其全部子路径
5. 手工把某用户的 `Entitlement.revokedAt` 置为过去时间，观察权限是否收回（**预期不收回 → DEF-001**）
6. 用 Web 的 Cookie 去调用移动端 API
7. 用移动端 Bearer Token 去调用 Web API
8. 令牌登出后立即重放同一个请求
9. 用考试题目 ID 调用检查点校验接口（`SEC-04` 边界）
10. 遍历所有 `SEC-NN` 标记的位置，逐个思考"绕过它的最简单方式是什么"

### 已知的高风险方向

> **第 1、5 条最可能出问题。**
> 第 1 条覆盖零测试的身份组合；第 5 条预期会复现 DEF-001，请完整记录证据。
> 第 10 条是一个**系统性方法**：代码里的 12 类 `SEC-NN` 标记是别人已经想清楚的安全不变量，逐个尝试绕过，比自己凭空想攻击面高效得多。

## CH-03 · 支付与权益状态机边界

| 项 | 内容 |
|---|---|
| **目标** | 找出支付流程中断、重复、异常时序下的权益状态错误 |
| **时间盒** | 120 分钟（含 Stripe 测试模式准备） |
| **范围** | 结账 → Webhook → 权益发放 → 权限生效 |
| **不含** | Stripe 自身的支付页面 |
| **优先级** | **P0** — 涉及资金 |

### 测试思路

1. 发起结账后**直接关闭页面**，不完成支付 → 检查是否产生残留记录
2. 完成支付后**立即**访问付费内容（Webhook 可能还没到）
3. 用 Stripe CLI **重放**同一个 Webhook 事件多次
4. **同一用户连续购买两次**同一商品
5. PAID 用户再购买 Flight Review（权益已隐含）
6. 支付成功后立刻登出再登录，检查权限
7. 在移动端购买，在 Web 端检查权限是否生效
8. 篡改 Webhook 请求体但保留原签名
9. 构造一个 `userId` 不存在的 Webhook 事件
10. 支付被拒（用 `4000 0000 0000 0002`）后立即重试成功

### 已知的高风险方向

> **第 2、4、5 条对应 PRD 未定义项**（U5、重复购买），预期会发现问题。
> 第 2 条是真实用户会遇到的场景：支付完成、回跳成功，但 Webhook 延迟——用户看到"未解锁"会非常困惑。**这是功能正确但体验有缺陷的典型交叉地带。**

## CH-04 · 双语与双端一致性

| 项 | 内容 |
|---|---|
| **目标** | 找出 EN/ZH 与 Web/移动端之间的行为漂移与内容缺失 |
| **时间盒** | 90 分钟 |
| **范围** | 全站主要用户路径 |
| **优先级** | P1 |

### 测试思路

1. 全程用 ZH 走一遍核心旅程，记录**所有出现英文的地方**
2. 全程用 EN 走一遍，记录**所有出现中文的地方**
3. 同一个功能在 Web 与移动端**逐项比对返回值**（尤其是权限相关的错误码）
4. 中途切换语言（答题中、结账中、预约中）
5. 中文输入：用户名、AI 助手提问框输入**全角字符、emoji、超长文本**
6. 检查邮件通知的语言是否跟随用户设置
7. 检查错误提示是否有未翻译的技术性文案（如直接暴露 `payment_required`）

### 输入探索的通用套路

对每一个输入框依次试：**空 · 零 · 负数 · 超长 · 特殊字符 · emoji · SQL 片段 · HTML 标签 · 前后空格 · 全角字符**

本项目是双语产品，**全角字符与 emoji 尤其值得试**——用户名、AI 助手输入框都是入口。

## CH-05 · 时间与并发

| 项 | 内容 |
|---|---|
| **目标** | 找出与时间、时序、并发相关的缺陷 |
| **时间盒** | 90 分钟 |
| **范围** | 全站有时效或有并发可能的功能 |
| **优先级** | P1 |

### 测试思路

1. 考试超时的各个边界（剩 1 秒交卷 / 剩 0 秒 / 超时后）
2. 验证码在第 9 分 59 秒与第 10 分 01 秒
3. 登录锁定期满后能否正常登录
4. 移动端令牌在第 29 天与第 31 天
5. **两人同时预约同一时段**
6. **同一用户两个设备同时作答**
7. 同一验证码被两个请求同时提交
8. 快速连点提交按钮 5 次
9. 修改系统时区后重试上述场景
10. 跨零点操作（例如 23:59 开始考试）

### 已知的高风险方向

> **第 6、8 条最可能出问题。**第 8 条也是排查低复现率缺陷的技巧：
> 手工点击难以触发的时序问题，用快速连点或脚本往往能把复现率从 3/20 拉到 10/10——**一旦稳定复现，隐藏变量就找到了。**

## 执行计划建议

| 时机 | 执行 |
|---|---|
| 首轮（学习/建立基线） | CH-01 → CH-02 → CH-03 |
| 每个迭代 | 至少 1 个 charter |
| 涉及支付改动的发布前 | CH-03 |
| 涉及权限改动的发布前 | CH-02 |
| 新增移动端功能后 | CH-04 |

### 首轮执行的成功标准

**至少找到 1 个真实缺陷。**

如果 90 分钟一个都没找到，通常不是产品太完美，而是探索的思路还停留在"正常使用"上——回到 charter 的"高风险方向"提示，专门往那些方向走。

从当前的代码审查结论看，CH-01 的第 7 条与 CH-02 的第 5 条**几乎必然会复现问题**（对应 DEF-002、DEF-001）。首轮执行的实际目标是**为这两个已知缺陷收集完整的复现证据**。
